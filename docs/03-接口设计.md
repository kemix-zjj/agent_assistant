## 1. 文档信息

| 项目 | 内容 |
|------|------|
| 风格 | RESTful，JSON over HTTPS |
| 基础路径 | `/api/v1` |
| 认证 | 网关统一登录态（Cookie / Header `Authorization`），服务层从登录态解析 `user_id`、`company_id`、`is_admin` |

### 1.2 接口文档的生成方式

本文档是**设计与契约层**的接口说明（人工维护）；运行时接口文档由 FastAPI 从代码自动生成，两者不是同一份产物。

| 产物 | 生成方式 | 地址 |
|------|---------|------|
| Swagger UI | FastAPI 内置页面，读取运行时的 OpenAPI 描述渲染 | `/docs` |
| ReDoc | 同上，另一种阅读版式 | `/redoc` |
| OpenAPI 3.1 描述 | 进程启动时扫描路由与 Pydantic 模型即时计算，不落盘 | `/openapi.json` |

生成逻辑集中在 [app/main.py](../server/app/main.py) 的 `FastAPI(...)` 装配，`docs_url` / `redoc_url` / `openapi_url` 三个参数决定上述地址；文档中的分组、标题、参数说明分别来自路由的 `tags`、`summary` 与 `Query(description=...)`。

| 文档内容 | 代码来源 |
|---------|---------|
| 路径、方法、状态码 | `app/api/v1/*.py` 的路由装饰器 |
| 请求体字段与校验（长度、枚举、去重） | `app/schemas/*.py` 的 Pydantic 模型（`ConfigDict(alias_generator=to_camel)`） |
| 分组与接口标题 | 路由的 `tags` 与 `summary` |
| 鉴权请求头 | `app/core/security.py` 的 `get_current_user` |

请求与响应示例由 Pydantic 生成，但**响应体字段不会出现在 `/docs` 中**：路由处理函数返回 `dict`，统一包装为 `{ code, message, data, traceId }`（[app/core/response.py](../server/app/core/response.py)），OpenAPI 只能把它描述为通用对象。实际返回字段以本文档 §3 ~ §9 为准；如需 `/docs` 也展示完整响应结构，需要给每个路由补 `response_model`。

导出静态描述文件（可选，用于归档或对接第三方工具）：

```powershell
# 后端启动后执行
curl.exe -s http://127.0.0.1:8000/openapi.json > docs/openapi.json
```

核对接口数量：

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/openapi.json).paths.PSObject.Properties.Count  # 当前 28 条路径 / 34 个操作
```

> 34 个操作 = 本文档 33 个业务接口 + `/health` 健康检查（不带 `/api/v1` 前缀，供探针直接访问）。

## 2. 通用约定

### 2.1 统一响应结构

成功：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "traceId": "b3f1c2d4e5a64f0f9c1e2a7b8d9e0f11"
}
```

失败：

```json
{
  "code": "ASSISTANT_NAME_DUPLICATED",
  "message": "助理昵称已存在，请修改",
  "data": { "field": "name" },
  "traceId": "b3f1c2d4e5a64f0f9c1e2a7b8d9e0f11"
}
```

- HTTP 状态码与业务错误码同时使用：4xx 表示客户端可修正问题，5xx 表示系统异常。
- 前端以 `code` 做文案映射，`message` 作为兜底展示。
- `data` 在无内容时返回 `null`，不使用空对象。

### 2.2 分页结构

```json
{
  "list": [],
  "total": 37,
  "page": 1,
  "pageSize": 12
}
```

### 2.3 共享范围对象（`scope`）—— 全链路统一

> 该结构在**创建向导共享设置、共享提交弹窗、共享范围弹窗、审批详情范围调整**四处完全一致（需求 4.0）。

```json
{
  "scopeMode": "RANGE",
  "orgs":      [{ "id": "O11",  "name": "人力资源部" }],
  "roles":     [{ "id": "r4",   "name": "招聘专员" }],
  "positions": [{ "id": "p1",   "name": "招聘专员" }],
  "users":     [{ "id": "u1",   "name": "李静", "deptName": "人力资源部 · 招聘组" }],
  "grantTotal": 8,
  "summary": "人力资源部、招聘专员 等 8 人"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `scopeMode` | enum | `RANGE` 范围授权 / `PUBLIC` 公开 |
| `orgs/roles/positions/users` | array | `PUBLIC` 模式下均为空数组 |
| `grantTotal` | int | 展开后授权人数；`PUBLIC` 时为公司在职人数 |
| `summary` | string | 列表与审批列表用的范围摘要，展示前 2 项 + `+N` |

## 3. 助理管理接口

### 3.1 GET /assistants · 助理团助理列表

**Query 参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `scope` | enum | 是 | `all` | `all` 全部 / `mine` 我的助理 / `shared` 共享助理 / `auth` 授权管理（仅公司管理员，非管理员返回 `NO_PERMISSION`） |
| `categoryId` | int | 否 | — | 分类筛选，不传为「全部」 |
| `keyword` | string | 否 | — | 按昵称与标签模糊搜索，≤50 字符 |
| `statusFilter` | enum | 否 | — | 仅 `scope=mine` 生效：`unshared`/`pending`/`approved`/`rejected` |
| `subscribeFilter` | enum | 否 | `subscribed` | 仅 `scope=shared` 生效：`subscribed`/`removed` |
| `page` | int | 否 | 1 | |
| `pageSize` | int | 否 | 12 | 最大 50 |

**各范围的数据口径**

| scope | 包含 | 不包含 |
|-------|------|--------|
| `all` 全部 | 平台预置 ∪ 我创建且 `approved` ∪ 别人共享给我且我 `subscribed` | 未共享、待审批、已拒绝、下架审批中、已下架、已移除订阅 |
| `mine` 我的助理 | 我创建的全部状态（`unshared`/`pending`/`approved`/`rejected`/`offline_pending`/`offline`） | 平台预置、别人共享给我的 |
| `shared` 共享助理 | 别人授权给我且 `grant_status=valid`（含已移除，可用 `subscribeFilter` 筛选） | 我自己创建的助理（即使我自己也在授权名单中） |
| `auth` 授权管理（仅管理员） | 全部自建 / 第三方且 `share_status ∈ {approved, offline_pending}` | 平台预置、未共享、已拒绝、已下架 |

```json
  "source": "shared",
  "shareStatus": null,
  "subscribeStatus": "subscribed",
  "sharedFrom": { "ownerName": "李静", "ownerDeptName": "人力资源部 · 招聘组" },
  "authorizedAt": "2026-10-12 09:00:00",
  "actions": ["summon", "remove"]

```

**授权管理卡片差异字段（`scope=auth`）**

授权管理页签只返回 `share_status ∈ {approved, offline_pending}` 的自建 / 第三方助理，卡片额外带范围摘要（`shareScope`），其余卡片字段与普通列表一致；`actions` 固定为 `["shareScope"]`。

```json
{
  "assistantId": 1001,
  "source": "custom",
  "shareStatus": "approved",
  "shareScope": { "scopeMode": "RANGE", "summary": "人力资源部、周涛 等 3 人", "grantTotal": 3 },
  "actions": ["shareScope"]
}
```

其他范围的卡片 `shareScope` 为 `null`。

**actions 派生规则**

| 场景 | actions |
|------|---------|
| 自建 + `unshared` | `summon`, `edit`, `delete`, `share` |
| 自建 + `pending` | `summon`, `edit`, `delete` |
| 自建 + `approved` | `summon`, `edit`, `delete`, `shareScope` |
| 自建 + `rejected` | `summon`, `edit`, `delete`, `resubmit` |
| 平台预置 + 管理员 | `summon`, `shareScope` |
| 平台预置 + 非管理员 | `summon` |
| 共享 + `subscribed` | `summon`, `remove` |
| 共享 + `removed` 且 grant valid | `resubscribe` |
| 共享 + `removed` 且 grant invalid | `[]`（展示「该助理授权已失效」） |

**排序**

- `scope=all`：平台预置在前（按 `created_at` 倒序）→ 我的助理（`created_at` 倒序）→ 共享助理（`grant_time` 倒序）
- `scope=mine`：`created_at` 倒序
- `scope=shared`：`grant_time` 倒序
- `scope=auth`：`updated_at` 倒序

**异常**

- `scope=shared` 且查询期间有助理被创建人删除 → 响应头带 `X-Removed-Shared-Count: 1`，前端展示「有 1 个共享助理已被创建人删除」

```json
{
```

```json
  "avatarType": "char",
  "avatarChar": "招",
  "avatarUrl": null,
  "avatarColor": "#3685F2",
  "description": "面向候选人与面试官的双向问答助理…",
```

**校验规则**

| 字段 | 规则 | 失败错误码 |

**统一入口**，覆盖：首次共享、被拒后重新提交、批量勾选提交。

|------|------|--------|
| 1 | `assistantIds` 非空、去重、≤20 | `PARAM_INVALID` |
| 2 | 每个助理存在、未删除、属于当前公司、创建人为当前用户 | `ASSISTANT_NOT_FOUND` / `ASSISTANT_NOT_OWNER` |

**分支逻辑**

| 场景 | 条件 | 行为 | 响应 |
|------|------|------|------|

### 7.4 PUT /approvals/{approvalId}/scope · 审批前调整范围

请求体：`{ "scope": { … } }`

**规则**

- 写一条新的 `share_scope(stage=adjusted, approval_id=当前单)`，不修改 `requested` 快照。
- `RANGE` 不可为空（`SHARE_SCOPE_EMPTY`），上限校验同前。
- 可在 `PUBLIC` 与 `RANGE` 之间切换（REQ-APR-DETAIL-010/011）。
- 仅暂存，审批通过时才写入 `assistant_grant`。
- 审批单非 `pending` → `APPROVAL_ALREADY_HANDLED`。

**响应**：`200` + 新的 `scope` 与 `scopeDiff`

### 7.5 POST /approvals/{approvalId}/approve · 审批通过

**请求体**

```json
{ "comment": "同意共享" }
```

**业务规则**

1. 条件更新 `approval SET status='approved', approver_*, final_scope_id=? WHERE id=? AND status='pending'`；受影响行数为 0 时读当前状态，已是 `approved` 则返回首次结果（幂等），否则 `APPROVAL_ALREADY_HANDLED`。
2. 最终范围 = `adjusted`（存在）否则 `requested`；为空时降级为 `requested`。
3. 展开最终范围为 `assistant_grant`（`grant_status='valid'`, `subscribe_status='subscribed'`）：
   - 新增人员插入；
   - 已有人员恢复 `valid`；
   - 原有效但新集合未命中的人员置 `invalid`（不物理删除，保留已移除历史）；
   - 被本次新命中且曾被移除的用户，订阅状态重置为 `subscribed`。
4. 更新 `assistant.share_status='approved'`、`authorized_count`、版本 minor +1。
5. `share` 类型：写 `assistant_version_history(action=share_approve)`。
   `scope_change` 类型：写 `assistant_version_history(action=scope_change)`。
6. 写审计（含变更前 / 后范围快照），失效待审批角标缓存。

**响应**

```json
{
  "approvalId": 9001,
  "status": "approved",
  "assistantId": 1003,
  "shareStatus": "approved",
  "grantTotal": 12,
  "approveTime": "2026-10-30 15:40:00"
}
```

### 7.6 POST /approvals/{approvalId}/reject · 审批拒绝

**请求体**

```json
{ "rejectReason": "授权范围包含外协单位组织节点，请收敛至本公司部门后重新提交。" }
```

| 校验 | 错误码 |
|------|--------|
| `rejectReason` 必填，1-200 字符 | `REJECT_REASON_REQUIRED` / `REJECT_REASON_TOO_LONG` |

**业务规则**

- 单事务：`approval` → `rejected` 并写 `reject_reason`/`approver`/`approve_time`；`assistant.share_status='rejected'` 并回写 `last_reject_reason`、`last_approver_name`、`last_approve_time`；写版本记录 `share_reject` 与审计。
- 管理员调整过的范围不予保存（需求：拒绝弹窗提示「授权范围调整将不予保存」），`adjusted` 快照保留但不转 `effective`。
- 幂等规则同 7.5。

**响应**

```json
{
  "approvalId": 9001,
  "status": "rejected",
  "assistantId": 1003,
  "shareStatus": "rejected",
  "rejectReason": "…",
  "approveTime": "2026-10-30 15:41:00"
}
```

## 8. AI 生成接口

### 8.1 POST /ai/generate

**请求体**

```json
{
  "field": "description",
  "name": "招聘面试助理",
  "categoryName": "人资",
  "description": null,
  "tags": [],
  "prompt": null,
  "quickQuestions": [],
  "currentValue": null,
  "mode": "auto"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `field` | enum | `description` / `tags` / `prompt` / `quickQuestions` |
| `mode` | enum | `auto`（服务端按 `currentValue` 是否为空判定生成 / 润色）/ `generate` / `polish` |
| `currentValue` | any | 当前字段已有内容：字符串，或标签 / 快速问题数组 |
| 其余 | — | 关联输入，随 `field` 取值不同使用不同字段 |

**字段规则（需求 4.1.1.0）**

| field | 为空（生成） | 已有内容（润色） | 输出约束 |
|-------|-------------|-----------------|---------|
| `description` | 依据 `name` + `categoryName` 生成 | 保留原描述意图后补充场景与依据说明 | 10-200 字符 |
| `tags` | 依据 `name` + `categoryName` + `description` 生成 5 个 | 基于已有标签补充至 5 个 | 每个 ≤8 字符，总数 ≤5，去重 |
| `prompt` | 依据 `name` / `description` / `categoryName` / `tags` 生成 | 结合 `name`、`description` 在现有提示词上补充要求 | ≤4000 字符 |
| `quickQuestions` | 依据 `name` + `description` 生成 | 在已有基础上结合 `name`、`description` 补充 | 去重合并，≤6 条，每条 ≤30 字符 |

**响应**

```json
{
  "field": "description",
  "mode": "generate",
  "value": "面向候选人与面试官的双向问答助理，可生成面试提纲…",
  "hitLimit": false
}
```

| 场景 | 响应 |
|------|------|
| 标签已满 5 个 | `200`，`hitLimit: true`，`value` 为原值，前端提示上限文案 |
| 快速问题已满 6 条 | 同上 |
| 关联字段全空 | 使用兜底输入（如名称兜底「业务助理」）正常生成 |
| 大模型未启用（`LLM_ENABLED=false` 或无 API Key） | `200`，服务端用确定性模板生成 |
| 大模型返回内容不合规（长度不足等） | `200`，服务端回退模板生成 |
| 大模型超时 / 失败 | `502` `AI_GENERATE_FAILED`，前端保留原内容 |

**实现说明**

- 大模型：OpenAI 兼容 `POST {LLM_BASE_URL}/chat/completions`，配置见 `server/.env` 的 `LLM_*` 项（默认网关 `https://nisai-tools-yc.nistone.com/v1`，模型 `huaweicloud/deepseek-v4.1-flash-1017`）。
- 封装位于 `server/app/services/llm_client.py`；调用时 `trust_env=False` 直连，并用系统证书库校验（企业内网 CA 不在 certifi 内置列表中）。
- 该模型为推理模型，先消耗 `reasoning_tokens` 再产出 `content`；请求固定带 `reasoning_effort=minimal` 以压低时延，`max_tokens` 默认 2000 避免正文被截空。
- 大模型输出一律经服务端二次校验（描述 10-200 字、提示词 ≤4000 字、标签 ≤8 字且 ≤5 个去重、快速问题 ≤30 字且 ≤6 条去重），不合规时回退模板。
- 前端请求超时单独放宽到 45s；服务端超时 30s。

**约束**：不参与助理保存事务；不落库；单测/离线环境通过 `LLM_ENABLED=false` 强制走模板。

## 9. 通用接口

### 9.1 POST /common/avatar-presign · 头像上传预签名

**请求体**

```json
{ "fileName": "avatar.png", "contentType": "image/png", "fileSize": 1048576 }
```

**校验**：`contentType` 以 `image/` 开头（`AVATAR_TYPE_INVALID`）；`fileSize ≤ 2097152`（`AVATAR_TOO_LARGE`）。

**响应**

```json
{
  "uploadUrl": "https://oss.example.com/presign?...",
  "objectKey": "avatar/2026/10/30/8f2c…png",
  "publicUrl": "https://cdn.example.com/avatar/2026/10/30/8f2c…png",
  "expiresIn": 600
}
```

前端直传对象存储后，把 `publicUrl` 作为 `avatarUrl` 提交到创建 / 编辑接口。

> 本期未接入对象存储，`uploadUrl` 返回本地上传接口 `/api/v1/common/avatar-upload`（§9.2），`publicUrl` 返回 `/static/...` 短路径；接入 OSS 后仅需替换 `common_service.build_avatar_presign`。

### 9.2 POST /common/avatar-upload · 头像上传（本地存储）

未接入对象存储时的可用实现：`multipart/form-data`，字段名 `file`。校验与 §9.1 一致（`image/*`、≤2MB），服务端落盘到 `server/static/avatar/YYYY/MM/DD/{hash}.{ext}` 并挂载为 `/static`。

**响应**（201）

```json
{
  "objectKey": "avatar/2026/11/09/8f2c1a3d5b7e9c01.png",
  "avatarUrl": "/static/avatar/2026/11/09/8f2c1a3d5b7e9c01.png"
}
```

把 `avatarUrl` 原样提交到创建 / 编辑接口即可（长度远小于 512 字符上限）。前端不允许把图片转 base64 塞进 `avatarUrl`——单张 1MB 图片的 dataURL 约 130 万字符，必然触发 `PARAM_INVALID`。

> 接入 OSS / S3 后：前端改回「预签名 → 直传 → 提交 `publicUrl`」链路，本接口可下线；`avatar_base_url` 配置对外域名后，`avatar_url` 会返回绝对地址。

## 11. 前后端交互约束

| 约束 | 说明 |
|------|------|
| 提交类按钮防重复 | 请求期间按钮 loading 且禁用；服务端以条件更新保证重复提交返回首次结果 |
| 列表三态 | 加载中 / 空态 / 加载失败（可重试），由 `code` 区分失败类型 |
| 失败保留输入 | 创建 / 编辑 / 共享提交失败时不清空表单与已选范围 |
| 状态漂移处理 | 409 类错误（`ASSISTANT_STATUS_CHANGED` / `APPROVAL_ALREADY_HANDLED` / `ASSISTANT_NOT_FOUND`）前端统一提示并刷新当前列表 |
| 范围组件一致性 | 四处共享范围场景共用同一组件，提交体均为 2.3 定义的 `scope` 结构 |
| 登录态失效 | 401 → 跳登录 → 回跳并保留 `scope`/`categoryId`/`keyword`（存 sessionStorage） |
| 列表刷新时机 | 提交共享、审批决策、移除 / 重新订阅成功后，前端就地刷新受影响列表与角标，不整页重载 |
