1FastAPI 在干什么

一句话：把「HTTP 请求」映射成「Python 函数调用」，再把返回值映射回「HTTP 响应」。参数解析、校验、序列化、错误处理它全包了。

它替你做的

  • 自动生成 OpenAPI / Swagger 文档
  • 基于类型注解的入参校验
  • 依赖注入（数据库会话、登录态、分页）
  • 统一异常到响应的翻译
  • 同步 / 异步共存

你仍要自己写的

  • 业务规则与状态机
  • 数据库事务边界
  • 错误码设计
  • 日志、鉴权策略、限流
  • 部署与进程管理

本项目的分层，决定了学习顺序

api/v1 路由→ services 领域服务→ repositories→ models → MySQL

FastAPI 只管第一层（api/v1）和它上面的一圈基础设施（core）。后三层是普通 Python 代码，FastAPI 不参与，因此更容易单独测试。

这条边界很重要：服务层不应该 import fastapi。如果发现某个 service 里出现了 HTTPException 或 Request，说明分层被破坏了。

2一次请求的旅程

以 GET /api/v1/assistants?scope=mine&pageSize=12 为例，请求进入后依次经过：

1
中间件：TraceMiddleware 生成 traceId，记录耗时；CORS 中间件补响应头
2
路由匹配：按注册顺序找到 list_assistants，抽取路径参数
3
参数解析与校验：查询参数按 Query 约束校验，Body 按 Pydantic 模型校验
4
依赖执行：先跑 get_db 拿 Session，再跑 get_current_user 解析身份
5
调用路由函数：函数体里只做「组装服务 + 调用 + 包装响应」
6
序列化：返回值经 UnifiedJSONResponse 输出 JSON
7
依赖清理：get_db 的 finally 关闭 Session
注意第 4 步和第 7 步：依赖的清理代码在响应发出后执行。所以不要在依赖里提前关闭数据库连接，也不要在 yield 之后做耗时的网络请求。

3应用装配与路由

对应文件：app/main.py、app/api/v1/__init__.py

创建应用

app = FastAPI(
    title=settings.app_name,
    version=settings.app_version,
    docs_url="/docs",           # Swagger UI，可直接试接口
    redoc_url="/redoc",
    openapi_url="/openapi.json",      # 前端/网关读取接口清单
    default_response_class=UnifiedJSONResponse,  # 全局默认响应类
)

启动后访问 http://127.0.0.1:8000/docs 即可看到所有接口。这也是最省事的联调工具——不需要 Postman。

三层路由嵌套

# 第 1 层：每个业务模块一个 APIRouter
router = APIRouter(prefix="/assistants", tags=["assistants"])

# 第 2 层：v1 汇总
api_router = APIRouter()
api_router.include_router(shares.router)
api_router.include_router(assistants.router)

# 第 3 层：挂到 app 上，统一加 /api/v1 前缀
app.include_router(api_router, prefix=settings.api_prefix)

最终路径 = /api/v1 + /assistants + /{assistantId}。

路由顺序 = 匹配优先级

# app/api/v1/__init__.py
# 助理详情为 /assistants/{id}，共享范围子路径需先注册以免被通配匹配
api_router.include_router(shares.router)      # 先
api_router.include_router(assistants.router)  # 后
FastAPI 按注册顺序匹配，先匹配到就返回。如果 /assistants/{id} 先注册，那么 /assistants/xxx/scope 这类路径可能被它吃掉，导致 422 或 404。规律：具体路径在前通配路径在后

4参数的五种来源

FastAPI 通过「参数的类型 + 声明方式」判断参数从哪里读。对应文件：app/api/v1/assistants.py、app/api/v1/common.py

来源声明方式本项目示例
路径参数 路径里写 {name}，函数同名参数 @router.get("/{assistantId}") + assistantId: int
查询参数 标量参数带默认值，或 Query() scope: str = Query(default="all")
请求体 参数类型是 Pydantic 模型 payload: AssistantUpsertPayload
请求头 Header(alias="X-User-Id") get_current_user 中的四个 Header
文件 UploadFile = File(...) /common/avatar-upload

一个函数里同时出现四种

@router.get("", summary="助理团助理列表")
def list_assistants(
    response: Response,                              # 直接注入 Response
    scope: str = Query(default="all"),              # 查询参数
    categoryId: int | None = Query(default=None),    # 保持前端驼峰命名
    paging: PageParams = Depends(),                  # 参数聚合依赖
    db: Session = Depends(get_db),                   # 资源依赖
    user: CurrentUser = Depends(get_current_user),    # 身份依赖
) -> dict:

不需要手写 request.query_params.get(...)。类型标注就是契约，同时也喂给了 OpenAPI 文档。

约束写在声明处

# 路径参数也可以加校验
assistantId: int = Path(ge=1, description="助理主键")

# 查询参数：范围约束 + 驼峰别名
page_size: int = Query(default=12, ge=1, le=50, alias="pageSize")

响应头也能改

# 前端据此展示「变更将立即对 N 个授权对象生效」
detail, affected = service.update_assistant(assistantId, payload, user)
if affected:
    response.headers["X-Affected-Grant-Count"] = str(affected)

注入 Response 对象后，返回值仍然照常走序列化，两者不冲突。

5依赖注入（核心）

一句话概括：函数声明「我需要什么」，FastAPI 负责准备、校验、缓存和清理。本项目有三类典型依赖。

类型一：带清理的资源依赖

文件：app/core/database.py

def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db              # yield 之前是准备
    except Exception:
        db.rollback()        # 异常自动回滚
        raise
    finally:
        db.close()           # yield 之后是清理

为什么用 yield

  • yield 之前是准备
  • yield 之后是清理
  • 异常时自动回滚，业务代码不写 try

带来的约定

  • 每个请求独立 Session，天然隔离
  • 不要在 service 里 commit 后继续用对象
  • 提交时机由服务层控制，依赖只负责收尾

类型二：依赖可以依赖依赖

文件：app/core/security.py

def get_current_user(
    x_user_id: str | None = Header(default=None, alias="X-User-Id"),
    x_company_id: str | None = Header(default=None, alias="X-Company-Id"),
) -> CurrentUser:
    if not x_user_id:
        raise UnauthenticatedError()          # 依赖里可以直接抛异常
    return CurrentUser(user_id=..., is_admin=...)

任何接口只要写 user: CurrentUser = Depends(get_current_user)，就自动获得登录态；没带 Header 时在进入函数体之前就返回 401。

这正是「鉴权前置」的实现方式：把校验放在依赖里，而不是每个函数开头写 if。同理还有 user.require_admin()，在服务层做管理员校验。

类型三：类作为依赖，聚合一组参数

文件：app/core/pagination.py

class PageParams:
    def __init__(
        self,
        page: int = Query(default=1, ge=1, description="页码，从 1 开始"),
        page_size: int = Query(default=12, ge=1, le=50, alias="pageSize"),
    ) -> None:
        self.page = page
        self.page_size = page_size

    @property
    def offset(self) -> int:
        return (self.page - 1) * self.page_size

用 Depends()（注意是调用，不是 Depends(PageParams)）依赖一个类时，FastAPI 会解析构造函数里的 Query 默认值。好处是分页规则只写一次，offset 计算也集中。

依赖缓存

同一个请求内，相同依赖只执行一次。所以即使三个地方都写了 Depends(get_db)，也只会创建一个 Session。这也是为什么可以放心把 get_current_user 挂在多个依赖上。

6Pydantic 入参校验

文件：app/schemas/assistant.py

一份模型，两个方向

class AssistantUpsertPayload(BaseModel):
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)

    name: str = Field(min_length=2, max_length=20)
    avatar_type: Literal["char", "image"] = "char"
    avatar_color: str = Field(default="#3685F2", pattern=r"^#[0-9A-Fa-f]{6}$")
    tags: list[str] = Field(default_factory=list, max_length=5)

    @field_validator("name", "description")
    @classmethod
    def _strip_text(cls, value: str) -> str:
        return value.strip()

同一个模型既用于入参（payload: AssistantUpsertPayload），也用于出参（model_dump(by_alias=True) 转回驼峰）。

四个必须掌握的点

能力写法作用
命名映射 alias_generator=to_camel Python 用 snake_case，接口收发 camelCase，两边互不妥协
字段约束 Field(min_length=..., pattern=..., max_length=...) 在声明处表达规则，不合法自动 400，不用写 if
枚举限定 Literal["char", "image"] 取值写错直接拒绝，比运行期判断更早
字段清洗 @field_validator 去空格、空串转 None，只做格式化不做业务
边界要分清：字段级规则放 Pydantic，跨字段 / 跨表规则放服务层。比如「共享范围人数超限」依赖主数据，必须放在 scope_service 里，不能塞进 schema。

列表也能约束

tags: list[str] = Field(default_factory=list, max_length=5)          # 最多 5 个标签
skill_ids: list[str] = Field(default_factory=list, max_length=20)   # 最多 20 个技能

Pydantic v2 中，列表的 max_length 就是元素个数上限。要限制每个元素的长度，用 list[Annotated[str, Field(max_length=8)]]。

7统一响应与异常

本项目没有在每个接口里手写 JSONResponse，而是用「包装函数 + 全局异常处理器」两层。

成功：ok() 包一层

# app/core/response.py
def ok(data: object = None) -> dict:
    return {"code": "OK", "message": "success", "data": data, "traceId": ""}

# 路由里
detail = service.get_detail(assistantId, user)
return ok(detail.model_dump(by_alias=True))

固定四段式：code / message / data / traceId。前端只需处理一种结构，不需要按接口写分支。

失败：抛异常，不返回错误码

# app/core/errors.py
class BizError(Exception):
    def __init__(self, code, message, data=None, http_status: int = 400):
        self.code = code
        self.message = message
        self.http_status = http_status

# 服务层直接抛
raise NotFoundError(ErrorCode.ASSISTANT_NOT_FOUND, "助理不存在")
# app/core/exception_handlers.py
@app.exception_handler(BizError)
async def _biz_error(_: Request, exc: BizError) -> JSONResponse:
    return JSONResponse(
        status_code=exc.http_status,
        content=_body(exc.code.value, exc.message, exc.data),
    )

这样做的好处

  • 服务层不依赖 HTTP，可脱离框架测试
  • 错误码集中定义，不会各写各的
  • 回溯清晰：异常栈直接指向出问题的地方

要注册的四类处理器

  • BizError → 业务错误
  • RequestValidationError → 参数错误
  • IntegrityError → 唯一键冲突
  • Exception → 兜底 500

把技术异常翻译成业务语言

# 数据库唯一键名 → 业务错误码，避免把约束名暴露给前端
_UNIQUE_CONSTRAINT_MAP = {
    "uk_assistant_company_name": (ErrorCode.ASSISTANT_NAME_DUPLICATED, "助理昵称已存在，请修改"),
    "uk_category_company_name": (ErrorCode.CATEGORY_DUPLICATED, "分类名称已存在"),
}

参数校验失败时，把 Pydantic 的字段定位信息转成 {"field": "name"} 返回，前端可以直接高亮对应输入框。

状态码怎么定

场景状态码code
创建成功201OK
参数不合法400PARAM_INVALID
未登录401UNAUTHENTICATED
无权限403NO_PERMISSION
资源不存在404XXX_NOT_FOUND
唯一键冲突 / 状态冲突409XXX_DUPLICATED
未预期异常500INTERNAL_ERROR
HTTP 状态码表达「类别」，code 表达「具体原因」。两者都要有，前端才既能用拦截器统一处理，又能针对具体错误给提示。

8中间件与静态资源

自定义中间件

文件：app/core/middleware.py

class TraceMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        trace_id = request.headers.get("X-Trace-Id") or new_trace_id()
        set_trace_id(trace_id)

        started = time.perf_counter()
        response: Response = await call_next(request)
        elapsed_ms = (time.perf_counter() - started) * 1000

        response.headers["X-Trace-Id"] = trace_id
        logger.info("%s %s -> %s (%.1fms)", request.method,
                    request.url.path, response.status_code, elapsed_ms)
        return response

call_next 之前是「请求阶段」，之后是「响应阶段」。中间件适合做横切关注点：链路 ID、访问日志、耗时统计、CORS、鉴权前置。

洋葱模型

Trace 外层→ CORS→ 路由函数→ CORS→ Trace 外层 
app.add_middleware(CORSMiddleware, ...)   # 先加 → 内层
app.add_middleware(TraceMiddleware)       # 后加 → 外层
后添加的在外层。所以 Trace 在最外，CORS 响应头也能被它记录到；如果反过来，CORS 中间件短路返回时就不会留下日志。

静态资源挂载

static_dir = settings.static_dir
static_dir.mkdir(parents=True, exist_ok=True)      # 目录不存在时自动建
app.mount("/static", StaticFiles(directory=str(static_dir)), name="static")

本项目只把它当作「未配置 OBS 时的本地回退」。生产环境头像是写入 OBS 并通过公网域名访问，不走这条路径。

10常见坑清单

#坑后果 / 正确做法
1 同步路由写成 async def 本项目用同步 SQLAlchemy，写成 async def 会阻塞事件循环。同步函数用 def，FastAPI 自动丢线程池
2 路由注册顺序颠倒 通配路径先注册会吃掉后续具体路径。具体路径在前
3 依赖里提前关闭资源 yield 之后的清理在响应发出后执行，不要在 yield 前 close
4 在依赖里做耗时操作 依赖会阻塞请求；重活放后台任务或服务层异步化
5 查询参数大小写写错 HTTP 头不区分大小写，但查询参数区分，pageSize 必须完全一致
6 只返回 dict 不包 ok() 前端拿到结构不一致，需统一走响应包装
7 服务层 import fastapi 分层被破坏，服务层无法脱离框架测试
8 生产环境用 --reload 会额外起进程监控文件，必须去掉，并用多 worker
9 改了代码没重启 本项目未开 --reload，改后端必须重启进程才生效
10 把所有规则塞进 Pydantic 跨字段 / 跨表规则放服务层，schema 只做单字段校验与清洗
