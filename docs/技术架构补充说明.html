本文档是《总体架构设计》的补充，分为三个标签页：图片上传与对象存储（OBS）的实现链路、后端目录结构与一次请求的数据流向、以及面向 Python 后端初学者的技术栈关键词速查。点击左侧标签切换。

1文档定位与结论速览

当前项目中唯一的图片场景是助理头像（预置头像 + 本地图片上传）。本方案把这部分从“后端本地磁盘”切换为“对象存储”，数据库与接口的行为约定如下。

维度约定
上传方式后端中转：前端 multipart/form-data 提交到上传接口，服务端校验后写入 OBS
存储服务天翼云 OBS，S3 兼容协议，桶 nistone-ai-assistant
对象 key 前缀test/assistant/avatar/YYYY/MM/DD/{digest}.{ext}
数据库字段assistant.avatar_url 只存对象 key（不含域名）
接口返回列表 / 详情 / 审批卡片 / 召唤记录统一返回完整可访问 URL
访问控制桶策略对 test/assistant/* 开放匿名只读，仅允许 s3:GetObject
本地回退未配置 OBS_AK/OBS_SK 时写 server/static，接口返回 /static/...，便于开发测试
预置头像（avatar-01~06.png）属于前端静态资源，随构建产物发布，不入 OBS；数据库只存 avatar_type='char' + avatar_char='P1'~'P6'。

2总体架构

图片只在“上传”时经过后端，读取时浏览器直接访问 OBS 域名，不占后端带宽。

写入链路

浏览器选图→ FastAPI 上传接口→ 校验 + 生成 key→ OBS 对象存储
浏览器提交表单→ 助理创建 / 编辑接口→ 剥离域名→ MySQL assistant.avatar_url（key）

读取链路

MySQL（key）→ 接口拼域名→ 浏览器拿到完整 URL→ OBS（匿名 GET）
组件职责
common_service.py校验类型与大小、生成对象 key、调用 OBS、拼接对外 URL、清理旧对象
obs_service.pyOBS 客户端封装：懒加载、私有 CA、上传、删除、公网 URL 生成
assistant_service.py创建 / 编辑时把提交的完整 URL 归一化为 key；换头像与删助理时触发清理
approval_service.py / summon_service.py输出头像时统一拼接完整 URL
config.pyOBS 连接参数、访问域名、对象前缀、本地回退开关

3存储模型：库里存 key，接口给 URL

这样做的好处是换域名、接 CDN 时数据库零迁移；前端拿到的始终是可直接渲染的完整地址。

数据库

-- assistant 表
avatar_type  'image'
avatar_url   'test/assistant/avatar/2026/11/16/fdb5412c5f30cdaf.png'

接口响应

{
  "avatarType": "image",
  "avatarUrl": "https://nistone-ai-assistant.fjoss.xstore.ctyun.cn/test/assistant/avatar/2026/11/16/fdb5412c5f30cdaf.png"
}

上传接口响应

{
  "objectKey": "test/assistant/avatar/2026/11/16/fdb5412c5f30cdaf.png",
  "avatarUrl": "https://nistone-ai-assistant.fjoss.xstore.ctyun.cn/test/assistant/avatar/2026/11/16/fdb5412c5f30cdaf.png"
}
前端必须使用返回的 avatarUrl 原样回填表单，不要自行拼接或改写；提交后由服务端负责转成 key。

4上传链路（后端中转）

接口：POST /api/v1/common/avatar-upload，multipart/form-data，字段名 file。

步骤动作失败处理
1前端校验：image/*、单文件 ≤ 2MB本地提示，不发请求
2后端校验 MIME 与字节长度AVATAR_TYPE_INVALID / AVATAR_TOO_LARGE
3扩展名白名单：png / jpg / jpeg / gif / webp，非法时按 MIME 兜底兜底为 png
4生成 key：{前缀}/{YYYY/MM/DD}/{sha256 前 16 位}.{ext}—
5写 OBS（未配置 AK/SK 时写本地 static）抛业务异常，前端提示重试
6返回 objectKey + 完整 avatarUrl—
 
# 对象 key 规则（common_service._object_key）
{obs_avatar_prefix}/{YYYY}/{MM}/{DD}/{digest16}.{ext}

# 当前取值
test/assistant/avatar/2026/11/16/fdb5412c5f30cdaf.png
上传接口与“保存助理”是两个独立动作：上传只写 OBS，不写数据库；点击保存 / 提交审批后，avatarUrl 才随助理数据落库。

5访问控制与桶策略

桶默认私有。为让 <img> 直接加载，对业务前缀开放匿名只读，且只授予读取权限。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadAssistantAssets",
    "Effect": "Allow",
    "Principal": "*",
    "Action": ["s3:GetObject"],
    "Resource": ["arn:aws:s3:::nistone-ai-assistant/test/assistant/*"]
  }]
}
项目说明
匿名权限仅 s3:GetObject；不含列举、上传、删除
私有 CA该域名使用私有根证书，需随服务部署 server/certs/endpoint-root-ca.pem，否则报 CERTIFICATE_VERIFY_FAILED
校验和兼容网关不支持 aws-chunked，客户端需设 request_checksum_calculation="when_required"，否则报 XAmzContentSHA256Mismatch
换域名 / CDN只改 OBS_PUBLIC_BASE，数据库 key 不变；桶策略的 Resource 按新前缀同步调整
预签名 URL会过期，禁止写入数据库；本期预签名接口仅作为直传演进预留

6回显与历史兼容

读取时统一经过一个转换函数，保证三种历史取值都能正常显示。

转换规则

avatar_url 存储值返回给前端说明
test/assistant/avatar/...{OBS_PUBLIC_BASE}/test/assistant/avatar/...当前标准形态
https://...原样返回迁移前的历史数据或外部图片
/static/...原样返回本地回退模式产生的数据
null / 空null使用前端默认头像

入口函数

函数触发时机
normalize_avatar_value()创建 / 编辑提交时：完整 URL → 对象 key
avatar_url_for()列表、详情、审批卡片、召唤记录：key → 完整 URL
delete_avatar()换头像 / 删助理：key、OBS URL、/static 路径均可识别
历史数据已完成迁移：原 /static/avatar/... 与早期完整 URL 均已转成 key，当前有效记录中不含本地路径与完整 URL。

7生命周期与清理

场景行为
首次上传并保存对象写入，key 落库
编辑时更换头像新对象写入；提交成功后删除旧 key 对应对象
删除助理软删除助理记录，同时删除其头像对象
删除失败只记录 warning 日志，不回滚业务主流程
预置头像 / 外部 URL不产生 OBS 对象，清理时直接忽略
上传多次只保存一次中间上传的图片会残留为无引用对象（已知限制）
当前未实现“临时对象自动回收”。如需彻底避免残留，可在上传接口增加“待替换的旧 key”，或增加按日期扫描的无引用对象清理任务。

1分层总览

后端按「一层只做一类事」切分。纵向是调用链，越往下越接近数据库；core/ 与 schemas/ 不属于任何单一层，而是横切在所有层之上。

前端请求→ api/→ services/→ repositories/→ models/→ MySQL
横切 core/ schemas/ 被多层同时 import，不参与单向下行
判断一个目录是不是「一层」，看依赖是否单向：api 依赖 service，service 依赖 repository，反向不允许。而 core 被每一层依赖、schemas 被 api 与 service 同时依赖，所以它们是横切层。

2各层职责

一句话概括：api 负责翻译，service 负责判断，repository 负责存取，model 负责映射。

目录职责依赖方向典型文件
api/翻译官：把 HTTP 参数翻译成 Python 参数，调用一个 service 方法，再把结果包成统一响应schemas、core、servicesapi/v1/assistants.py
services/业务规则：参数校验、权限判断、状态机流转、事务编排、出参组装repositories、models、schemas、coreservices/assistant_service.py
repositories/数据访问：只做查询与持久化，不含权限判断与业务规则models、core（Session）repositories/assistant_repo.py
models/ORM 模型：表结构映射，一个类对应一张表，一个属性对应一列SQLAlchemymodels/assistant.py
schemas/接口契约：出入参的字段、类型、camelCase 别名被 api 与 service 依赖schemas/assistant.py
core/横切基础设施：配置、数据库会话、身份解析、错误码、统一响应、日志、中间件被以上所有层依赖core/database.py

3一次「查列表」的完整流转

以 GET /api/v1/assistants（助理团助理列表）为例，同一份请求数据要经过七个环节。

#所在层动作代码位置
1apiUvicorn 收到连接，FastAPI 匹配到 list_assistants；Depends 注入数据库会话与当前用户api/v1/assistants.py
2api → service参数原样下传，api 不做任何判断assistants.py
3service校验 scope / statusFilter / subscribeFilter / keyword 的取值是否合法assistant_service.py
4service → repo调用 list_ids，拿到「当前页的 id 列表 + 总数」assistant_service.py
5repo拼 select ... where（三范围 UNION），SQLAlchemy 生成 SQL，PyMySQL 执行assistant_repo.py
6service按 id 批量查详情与授权信息，逐条 _to_card 组装成 Pydantic 对象assistant_service.py
7apimodel_dump(by_alias=True) 转字典，ok() 包成统一响应assistants.py
 
# ① api/v1/assistants.py —— 只做翻译与投递
service = AssistantService(db)
page = service.list_assistants(user, scope=scope, category_id=categoryId, ...)
return ok(page.model_dump(by_alias=True))

# ② services/assistant_service.py —— 判断与组装
ids, total = self.repo.list_ids(...)          # 只拿 id + 总数
rows       = self.repo.load_many(ids)         # 再批量查详情
grants     = self.repo.find_grants(...)
cards = [self._to_card(row, grants.get(row.id), user, scope) for row in rows]
return AssistantPage(list=cards, total=total, page=page, page_size=page_size)
api 层从头到尾没有出现一次业务判断：它不知道「scope 为 all 时要折叠审批状态」，也不知道头像要拼域名。这些都属于 service。

4数据形态的四次转换

同一份数据在链路里换了四次外形，每次转换都有明确的负责人。

形态载体谁产生关键变化
① ORM 行Assistant 实例repositories与表列一一对应；created_at 是 datetime，category 是关系对象
② 业务对象AssistantCard 实例services已格式化、按视角折叠、派生 actions；这些字段数据库里并不存在
③ 纯字典dictservices 内调用 model_dump键名由 snake_case 变为 camelCase
④ 统一响应{code, message, data, traceId}api 层 ok()前端最终拿到的 JSON
 
# ① repositories 交出的 ORM 行
row.created_at       → datetime(2026, 11, 16, 9, 30)
row.category.name    → "效率工具"

# ② services 组装后的 Pydantic 对象
created_at    = _fmt_required(row.created_at)                  → "2026-11-16 09:30:00"
category_name = row.category.name if row.category else ""
actions       = self._derive_actions(row, grant, user)         # 库里没有，按角色计算

# ③ api 层 model_dump(by_alias=True)
{"assistantId": 1, "createdAt": "2026-11-16 09:30:00", "actions": [...]}
ORM 行对象是「数据库的样子」，Pydantic 模型是「接口的样子」，中间那次转换由 service 负责——它也是唯一知道「这个值该是什么」的地方。

5core 与 schemas 的定位

core/ 不调用任何业务层，只被调用。它把「每个请求都要用、但与业务无关」的东西收在一起。

文件职责
config.py读 .env 提供全局配置：数据库、LLM、OBS、头像限制
database.pyEngine 连接池、SessionLocal、依赖注入的 get_db
security.py从请求头解析 CurrentUser，判定管理员
errors.py / exception_handlers.py业务错误码与异常类；全局异常转统一响应结构
response.py / json_response.pyok() / fail() 响应包装；时间、Decimal 的自定义编码
middleware.py / logging.pytraceId、访问日志、耗时统计；日志格式与输出
pagination.py / timeutils.py分页参数 PageParams；统一时间获取

schemas 的边界

schemas 只描述接口形状，不持有业务逻辑（computed_field 这类纯派生除外）。

场景谁使用说明
入参apiFastAPI 把请求体 / query 解析成 Pydantic 对象并校验
出参servicesservice 逐字段构造 Pydantic 对象后返回
是否下传到 repo / model否仓储层与模型层完全不认识 schemas，只接收普通参数
一条实用判断：如果一个模块同时被三层以上 import，它就是横切层，不该塞进调用链。

1后端技术栈关键词速查

面向未接触过 Python 后端的读者。先把名词放回它所在的链路位置，再看逐词解释——脱离链路背名词，很容易把 models 和 schemas 这类名字相近的东西混在一起。

一次请求经过谁

前端 fetch→ Uvicorn（收连接）→ FastAPI（找路由）→ Pydantic（校验参数）→ service（业务判断）→ SQLAlchemy ORM→ MySQL
Alembic 不在请求链路上。它只在开发期使用：对比代码里的 ORM 模型与数据库真实表结构，生成改表脚本。

服务与框架

关键词一句话解释项目中的位置
Uvicorn用 Python 写的 Web 服务器进程，负责监听端口、接收 TCP 连接、把 HTTP 解析后交给应用。uvicorn app.main:app --reload 启动的就是它app/main.py 顶部注释
ASGI服务器与应用之间的协议标准。Uvicorn 是 ASGI 服务器，FastAPI 是 ASGI 应用，两者靠这个标准对接，因此可以互换requirements.txt 的 uvicorn[standard]
FastAPIWeb 框架：路由表、参数提取、依赖注入、中间件、自动文档。所有 @router.get(...) 都归它管app/main.py 的 create_app()
OpenAPI / SwaggerFastAPI 根据代码自动生成的接口描述，/docs 是可交互页面，可直接在页面上发请求app/main.py 的 docs_url="/docs"
APIRouter一组路由的集合。APIRouter(prefix="/assistants") 定义后由主 app 统一挂载app/api/v1/__init__.py

数据契约

关键词一句话解释项目中的位置
PydanticPython 的数据校验与序列化库。用类声明「要哪些字段、什么类型」，创建对象时自动校验与类型转换，也能一键导出成 dict / JSONapp/schemas/ 全部文件
Schema（Pydantic 模型）继承 BaseModel 的类，描述接口入参 / 出参的形状。它不是数据库表schemas/assistant.py 的 AssistantCard
BaseSettings / pydantic-settingsPydantic 的配置扩展：读环境变量与 .env，把 DB_HOST=xxx 变成 settings.db_host 并校验类型core/config.py 的 Settings
model_dump()把 Pydantic 对象转成 dict；by_alias=True 让 assistant_id 输出为 assistantId每个 api 函数的最后一行
computed_field只存在于出参、数据库里没有的派生字段，例如描述截断schemas/assistant.py 的 description_truncated

数据库

关键词一句话解释项目中的位置
ORMObject-Relational Mapping，对象关系映射：用类代表表、属性代表列、对象代表一行。写 row.name，底层自动变成 SQL，不必手写查询语句app/models/ 整个目录
ORM 模型具体那个类。例如 Assistant 对应 assistant 表，__tablename__ 指定表名，每个 mapped_column 对应一列models/assistant.py
SQLAlchemyPython 最主流的 ORM 库（2.0 版本）。Mapped、select()、relationship() 都来自它requirements.txt 的 SQLAlchemy>=2.0.36
PyMySQL纯 Python 的 MySQL 驱动，负责把 SQL 真正通过网络发给 MySQL 并读回结果。连接串 mysql+pymysql:// 中的 pymysql 就是它core/config.py 的 database_url
Engine连接池：维护一批复用的数据库长连接，避免每次请求都重新建连core/database.py 的 engine
Session一次业务对话：在其中查询、修改，最后 commit() 提交或 rollback() 回滚；请求结束自动关闭core/database.py 的 get_db
Alembic数据库版本控制 / 迁移工具，与 SQLAlchemy 同源。对比 ORM 模型与真实表结构，生成 ALTER TABLE 脚本并记录已执行版本server/alembic.ini、server/migrations/env.py
Migration（迁移）一次「改表结构」的脚本，有编号、可回滚、可重复执行server/migrations/
当前项目建表以 deploy/mysql/assistant_mysql.sql 为准，Alembic 只完成了环境接线（env.py 已绑定 settings.database_url 与 Base.metadata），尚无实际迁移版本文件，属于「预留未启用」。

框架机制

关键词一句话解释项目中的位置
依赖注入（Depends）参数上写 db: Session = Depends(get_db)，框架在调用前自动执行 get_db() 并注入结果，请求结束自动收尾（关连接、异常回滚）api/v1/assistants.py
中间件（Middleware）横在请求进入与响应返回之间的统一处理层：补 traceId、记访问日志、算耗时core/middleware.py 的 TraceMiddleware
CORS跨域许可。前端 5173、后端 8000 属于不同源，浏览器默认拦截，必须后端显式声明允许来源app/main.py 的 CORSMiddleware
统一响应包装所有接口都返回 {code, message, data, traceId} 同一形状，由 ok() / 异常处理器保证core/response.py、core/exception_handlers.py
