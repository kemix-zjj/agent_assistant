01前端与后端到底差在哪

先破除一个常见误解：后端不是「另一个写页面的地方」。

前端运行在用户的浏览器里，代码和请求参数用户都能改；后端运行在公司的服务器里，用户看不到代码，只能通过 HTTP 敲门。这个物理位置差异，决定了后端必须承担「可信裁判」的角色。

维度前端后端（本项目）
运行位置用户浏览器公司服务器 / 容器
代码可见性打包后用户可下载、可改用户看不到，只能调接口
主要职责展示、交互、表单体验、状态管理鉴权、校验、业务规则、数据持久化
数据从哪来内存 / 接口MySQL、对象存储、大模型等
出错的代价页面白屏、体验差数据错乱、越权、资损
典型技术Vue 3、TS、Vite、Element PlusPython、FastAPI、SQLAlchemy、MySQL
怎么调试DevTools、Vue Devtools终端日志、Swagger、pytest、数据库客户端

用餐厅打一个比方

前端 = 菜单 + 服务员

把菜品（功能）展示给顾客，记录顾客点了什么，把订单送到后厨，再把菜端回来。服务员可以态度很好、界面很漂亮，但不能自己决定免单。

后端 = 后厨 + 仓库 + 保安 + 账本

后厨按配方做菜（业务逻辑），仓库保管食材（数据库），保安检查谁能进后厨（鉴权），账本记录每一笔操作（审计日志）。顾客说「我是老板」，保安不能信，要查工牌。

数据库 = 仓库

食材不能堆在地上，要分区域、贴标签、登记出入库。表就是货架，字段就是标签，索引就是目录，事务就是「要么整单入库，要么整单退回」。

HTTP = 点餐单

服务员和后厨之间靠一张标准格式的单子沟通：桌号（URL）、要做什么（方法）、备注（Body）、特殊要求（Header）。后端不认识「服务员」，只认这张单子。

后端每天真正在处理的 6 件事

① 接收

从 HTTP 请求里取出路径、查询参数、Body、Header。

② 校验

字段长度、枚举取值、必填、格式、关联资源是否存在。

③ 鉴权

你是谁、属于哪个公司、是不是创建人、是不是管理员。

④ 业务

状态能不能流转、版本怎么算、范围怎么展开。

⑤ 持久化

开事务、写多张表、提交或回滚、保证一致性。

⑥ 响应

组装数据、脱敏、统一格式、错误码、traceId。

必懂 前端隐藏一个按钮，只是「不让你点」，不是「不让你做」。用户完全可以在 DevTools 里直接发请求。所以后端每个接口都要重新判断一次：这个用户、这个公司、这个资源、这个状态，允不允许。

后端代码为什么看起来比前端「绕」

因为后端要处理很多前端不需要处理的情况：两个人同时点审批、请求重复提交、数据库写到一半失败、用户伪造公司 ID、旧数据没有新字段、外部大模型超时。这些情况让代码必须分层、必须有事务、必须有兜底。你看到的「绕」，大多是在处理异常路径。

前端类比 前端写一个表单，正常路径可能 30 行；但加上 loading、空状态、错误提示、防重复提交、字段级报错、权限隐藏，就变成 150 行。后端也是一样，正常路径很短，大部分代码在处理「万一」。

02一次请求的完整旅程

这是整份笔记最重要的一节。看懂这条链路，后面的知识才有地方挂。

我们以「打开助理列表页，查询我的助理」为例。页面上你只是点了一个页签，但背后发生了十几步。先看全貌，不要纠结每个名词，后面会逐个拆。

浏览器点击→ axios 拦截器→ Vite 代理 / 网关→ Uvicorn→ FastAPI→ 路由 + 依赖→ Service→ Repository→ MySQL

12 步拆解

① 页面触发请求

助理列表页调用 getAssistants({ scope: 'mine', page: 1 })。这层是前端 API 封装，和页面解耦。

② axios 请求拦截器补登录态

开发期没有真实网关，前端在 web/src/api/request.ts 里按当前角色塞入 X-User-Id、X-Company-Id、X-User-Name。中文姓名要先百分号编码，因为 HTTP Header 只允许 ASCII。

③ 请求发到 8000 端口

开发环境浏览器访问的是 localhost:5173，Vite 把 /api 代理到 127.0.0.1:8000。生产环境通常由 Nginx / 网关转发，并顺便做登录校验。

④ Uvicorn 接收 TCP 请求

Uvicorn 是 ASGI 服务器，负责监听端口、解析 HTTP、把请求交给 FastAPI。你可以把它理解成「后端的 Vite Dev Server」，但它不负责业务。

⑤ FastAPI 经过中间件

请求会经过 CORS（判断哪个前端源可以跨域）和 TraceMiddleware（生成 traceId、记录耗时）。中间件像前端路由守卫，但它包住的是每一次请求。

⑥ 路由匹配

FastAPI 根据 GET /api/v1/assistants 找到 app/api/v1/assistants.py 里的 list_assistants 函数。找不到就 404，方法不对就 405。

⑦ 依赖注入准备「上下文」

Depends(get_db) 打开一个数据库会话；Depends(get_current_user) 解析 Header 得到当前用户；Depends() 解析分页参数。依赖像「函数参数的外卖」，框架先帮你准备好再调用函数。

⑧ Pydantic 解析并校验参数

Query 参数按类型转换，Body 按模型校验。长度不够、枚举不对、类型不对，在这里就会被拦下，返回 400（项目把 FastAPI 默认的 422 统一成了 400）。

⑨ Service 执行业务规则

AssistantService.list_assistants 校验 scope 取值、清理关键词、决定「我的 / 共享 / 全部」怎么查、最后把 ORM 对象组装成响应模型。

⑩ Repository 把业务翻译成 SQL

AssistantRepository.list_ids 用 SQLAlchemy 拼出三段 UNION 查询，先拿当前页的 ID 和总数；load_many 再批量加载完整对象，避免一条条查。

⑪ MySQL 执行 SQL 并返回结果

数据库只认 SQL，不认 Python 对象。SQLAlchemy 负责把 select(...) 变成 SQL，再把结果行变成 Python 对象。数据库里的表、索引、事务在这一层生效。

⑫ 响应一路回到浏览器

Service 返回 AssistantPage，路由用 ok(...) 包成 { code, message, data, traceId }，UnifiedJSONResponse 补上 traceId，序列化成 JSON。axios 响应拦截器判断 code === 'OK' 后剥掉外壳，页面拿到 data.list 开始渲染。

前端类比 这条链路很像 Vue 的一次更新：用户点击（事件）→ 调用 store action（axios）→ 发请求（HTTP）→ 后端返回（响应）→ store 更新（Service 组装）→ 组件重新渲染（JSON）。区别是后端每一步都可能失败，而且失败必须留下可追踪的记录。
记住这张图 以后遇到任何问题，先问自己：现在卡在哪一层？ 浏览器没发出请求？代理没转发？路由没匹配？参数校验没过？Service 抛错？SQL 写错？响应格式不对？定位到层，问题就解决一半。

为什么路由层不能写业务？

反例路由里塞满判断

@router.post("")
def create(payload, db=Depends(get_db), user=Depends(...)):
    if payload.name in [x.name for x in db.query(...)]:
        raise HTTPException(409, "重名")
    if user.user_id != ...:
        raise HTTPException(403, "无权限")
    row = Assistant(**payload.model_dump())
    db.add(row); db.commit()
    return row

问题：无法复用、无法单测、换个入口（定时任务/消息队列）就要复制一遍。

本项目写法路由只做三件事

@router.post("", status_code=201)
def create_assistant(payload, db=Depends(get_db), user=Depends(...)):
    service = AssistantService(db)
    detail = service.create_assistant(payload, user)
    return ok(detail.model_dump(by_alias=True))

路由像服务员：接单、转述、上菜。配方和库存检查都在后厨（Service）。

四个角色的「一句话人设」

路由：翻译官

把 URL、Header、Body 翻成 Python 参数；把 Service 的返回值翻成统一 JSON。它不应该知道「什么是共享」「版本号怎么算」。

Service：大脑

知道所有业务规则：谁能编辑、什么状态能删、审批通过后版本怎么变、事务什么时候提交。

Repository：手

只负责「怎么查、怎么存」。它像一个高级 SQL 生成器，不知道查出来的数据要用来干什么。

Model：账本格式

描述表结构、字段类型、外键、关系。它不知道接口长什么样，也不知道前端叫 assistantId 还是 id。

前端类比 这很像 Vue 项目里的「页面 → composable/store → API 层 → 类型定义」。页面不直接拼 axios URL，store 不直接操作 DOM，API 层不关心页面怎么渲染。分层的目的不是好看，而是改一处不影响一片。

为什么 Model 和 Schema 要分开？

因为「数据库怎么存」和「接口怎么传」经常不一样：

  • 数据库字段叫 share_status，前端要 shareStatus。
  • 列表卡片不能返回 prompt（提示词），详情才返回。
  • 被授权方看详情时，共享状态要折叠成「已共享」，不能暴露对方的审批 / 拒绝子类。
  • 数据库存的是 pending + pending_type，前端要展示「审批中 · 共享审批」。

如果直接把 ORM 对象丢给前端，字段名、脱敏、派生字段都会失控，还容易把内部字段泄露出去。Schema 就是那道出口安检。

判断新代码放哪 「这段代码如果换一个入口（定时任务、CLI、消息队列）还要不要？」要 → Service；只是 HTTP 相关 → api；只是查库 → Repository；只是数据形状 → Schema；只是表结构 → Model。

状态码：HTTP 的「结果标签」

状态码含义本项目什么时候出现
200成功查询、编辑、删除成功
201已创建创建助理成功（路由上显式声明）
400请求参数不合法scope 取值错、描述太短、字段校验失败
401未登录 / 登录态失效没带 X-User-Id
403已登录但没权限非管理员进审批中心、非创建人编辑
404资源不存在助理不存在、审批单不存在
409和当前状态冲突重名、已共享还想删、审批已被处理
422FastAPI 默认的校验失败被项目统一转成 400，前端基本看不到
500服务器内部错误未捕获异常、数据库挂了
前端类比 状态码像 Promise 的 resolve/reject，但更细：2xx 是 resolve；4xx 是「你这边有问题」；5xx 是「服务器这边有问题」。排查时先看状态码，能立刻判断该找谁。

状态码之外，还有业务错误码

本项目所有响应（包括错误）都带一个 code 字段：HTTP 状态码告诉网络层「大概哪类问题」，业务 code 告诉前端「具体是哪个问题」。例如：

409 + ASSISTANT_NAME_DUPLICATED
HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "code": "ASSISTANT_NAME_DUPLICATED",
  "message": "助理昵称已存在，请修改",
  "data": { "field": "name" },
  "traceId": "9f1c2e7a..."
}

前端拿到 data.field === 'name'，就能把错误提示精确标在「助理昵称」输入框下面，而不是弹一个笼统的 Toast。这就是「字段级错误定位」。

06FastAPI 路由：URL 怎么变成函数

路由是后端的「页面路由表」，但映射的不是组件，而是函数。

Vue Router 把 /assistant/list 映射到 AssistantList.vue；FastAPI 把 GET /api/v1/assistants 映射到 list_assistants() 函数。你不需要手动 if url == ...，装饰器已经登记好了。

server/app/api/v1/assistants.py · 路由声明
from fastapi import APIRouter, Depends, Query, Response, status

# prefix 统一加在每条路径前；tags 决定 Swagger 里的分组
router = APIRouter(prefix="/assistants", tags=["assistants"])

# 装饰器 = 登记：GET + 空路径 → 实际 URL 是 /api/v1/assistants
@router.get("", summary="助理团助理列表")
def list_assistants(
    response: Response,
    scope: str = Query(default="all", description="all / mine / shared"),
    categoryId: int | None = Query(default=None),
    paging: PageParams = Depends(),
    db: Session = Depends(get_db),
    user: CurrentUser = Depends(get_current_user),
) -> dict:
    service = AssistantService(db)
    page = service.list_assistants(user, scope=scope, ...)
    return ok(page.model_dump(by_alias=True))

装饰器到底做了什么

@router.get("") 不是「调用这个函数」，而是登记：把这个函数和「GET + 空路径 + 参数说明 + 返回说明」一起记到路由表。应用启动时，include_router 再把这张表合并进 FastAPI。

路由文件为什么这么短

因为所有业务都下沉到 Service 了。路由只做三件事：收参数 → 调 Service → 包响应。你可以把路由想象成「接口的 TypeScript 声明 + 一行调用」，真正的实现不在这里。

前端类比 路由文件像 Vue 的 routes.ts：只声明「什么 URL 对应什么组件」，不写组件内部逻辑。FastAPI 的路由函数同时承担了「声明」和「入口」，但真正干活的仍然是 Service。

为什么 /docs 能自动生成？

因为 FastAPI 从你的类型注解、Query(description=...)、Pydantic 模型、summary 里提取信息，生成一份 OpenAPI JSON。Swagger UI 再把它渲染成网页。所以：

  • 参数名、类型、默认值、说明都会出现在文档里。
  • 改代码 = 改文档，不会出现「文档和接口不一致」。
  • Pydantic 模型越清晰，文档越好用。

07Pydantic：请求进门前先过安检

前端表单校验是「体验」，Pydantic 校验是「守门」。两者都要有，但后者才是真的。

Pydantic 是 FastAPI 的「数据形状 + 校验」库。你定义一个类，写清楚每个字段的类型和限制，FastAPI 就会自动：把 JSON 转成 Python 对象、检查类型、检查长度、检查枚举、失败时返回错误。

自定义校验：Field 表达不了的规则

# 去除首尾空格：用户输入 " 招聘助手 " 应该存 "招聘助手"
@field_validator("name", "description")
@classmethod
def _strip_text(cls, value: str) -> str:
    return value.strip()

# 标签：不能空、单个不超过 8 字、不能重复
@field_validator("tags")
@classmethod
def _check_tags(cls, value: list[str]) -> list[str]:
    result: list[str] = []
    for tag in value:
        name = tag.strip()
        if not name:
            raise ValueError("标签不能为空")
        if len(name) > 8:
            raise ValueError("单个标签不超过 8 个字符")
        if name in result:
            raise ValueError("标签不能重复")
        result.append(name)
    return result

这是 FastAPI 最核心的设计。看懂它，路由参数里那些「没传却有值」的变量就都解释得通了。

依赖一：get_db —— 每个请求一个会话

server/app/core/database.py
def get_db() -> Generator[Session, None, None]:
    """FastAPI 依赖：每个请求一个会话，异常回滚，结束关闭。"""
    db = SessionLocal()
    try:
        yield db          # 把会话交给路由函数使用
    except Exception:
        db.rollback()      # 出异常就撤销本次请求的所有未提交修改
        raise
    finally:
        db.close()         # 无论成功失败都归还连接

yield 是「暂停在这里，等路由函数执行完再回来」。所以整个生命周期是：

创建 Session→ yield 给路由→ 路由/Service 读写→ 成功：close / 异常：rollback → close
为什么不能全局一个 Session 数据库会话不是线程安全的，也不是「一个连接大家一起用」。全局会话会导致：请求 A 的事务影响请求 B、连接不释放、并发下数据串台。FastAPI 每个请求创建一个，是最小隔离单元。

依赖二：get_current_user —— 从 Header 得到用户

        raise UnauthenticatedError()       # 没登录 → 401
    ...

几个细节：

  • Header(alias="X-User-Id")：HTTP Header 名带连字符，Python 变量名不能，所以用 alias 映射。
  • unquote：HTTP Header 只能放 ASCII，中文姓名是前端百分号编码后传的，这里解码。
  • _ADMIN_USER_IDS = {9001}：开发期用固定 ID 模拟管理员，接网关后应由网关注入 is_admin。
  • 没登录直接抛 UnauthenticatedError，全局异常处理器转成 401，路由函数根本不会执行。

        self.page_size = page_size

    @property
    def offset(self) -> int:
        return (self.page - 1) * self.page_size

所有需要分页的接口都写 paging: PageParams = Depends()，不用重复声明 page/pageSize。注意 Depends() 没传参数，FastAPI 会根据类型注解 PageParams 自动实例化。

前端类比 依赖注入很像 Vue 的 provide / inject 或 React 的 Context：子组件不自己 new 一个全局对象，而是声明「我要用这个上下文」，由上层提供。区别是 FastAPI 的依赖可以按请求创建、可以嵌套、可以在测试里替换。

09数据库与 SQL 入门

后端真正的「硬盘」。前端状态刷新就没了，数据库里的数据要一直在。

数据库不是「一个很大的 JSON」。它是有结构、有约束、有事务的数据仓库。你可以先把它想成一组 Excel 表：每张表有列名和类型，每行是一条记录，表之间用 ID 关联。

六个必须知道的词

表 Table

一类数据的集合，比如 assistant 存所有助理。类似前端的一个数组，但每项结构固定。

行 Row / 记录

表里的一条数据，比如「招聘助手」这个助理。类似数组里的一个对象。

列 Column / 字段

一条记录有哪些属性，比如 name、share_status。类似对象的 key。

主键 Primary Key

这一行的唯一身份证，通常是自增 id。前端列表的 key 就靠它。

外键 Foreign Key

指向另一张表的主键，表示「属于谁」。比如 assistant.category_id 指向分类表。

索引 Index

加速查询的目录。唯一索引还能防止重复，比如同一公司不能有同名助理。

为什么用「逻辑删除」而不是真删？

看 assistant 表里的 deleted_at。删除助理时，项目不是 DELETE FROM assistant，而是把 deleted_at 设为当前时间。所有查询都带 deleted_at IS NULL。

逻辑删除的好处

  • 历史审批、审计日志还能关联到对象
  • 误删可恢复
  • 唯一键可以用生成列处理「删除后同名可重建」

代价

  • 每条查询都要记得过滤
  • 表会越来越大
  • 唯一索引要配合生成列，不能直接建在 name 上

索引：让查询不用翻完整本书

没有索引，数据库要从第一行扫到最后一行（全表扫描）。有索引，就像书的目录，能直接跳到目标页。

索引作用项目里的意义
uk_assistant_company_name同一公司内助理名唯一重名直接 409，Service 先查只是为了友好提示
uk_category_company_name同一公司内分类名唯一分类重名拦截
uk_approval_pending_assistant同一助理同时只能有一条待审批并发提交时数据库兜底
公司 + 状态 / 创建人 等普通索引加速列表筛选助理列表、审批中心的常用条件
进阶 索引不是越多越好：每个索引都会占空间、拖慢写入。给「经常出现在 WHERE / ORDER BY / JOIN 的列」建索引，而不是给每个字段都建。

事务：要么全成，要么全不成

「提交共享」要同时写：审批单、范围快照、范围明细、助理状态、版本记录、审计日志。如果写到一半数据库挂了，只写了一半，数据就乱了。事务保证这些操作打包成一个原子操作。

事务的四个字母（ACID）
A 原子性 Atomicity   ：要么全做，要么全不做
C 一致性 Consistency ：约束前后都成立（外键、唯一键、非空）
I 隔离性 Isolation   ：并发事务互不干扰（隔离级别控制）
D 持久性 Durability  ：提交后掉电也不丢（靠日志与刷盘）

在代码里，事务边界通常就是 db.commit()。Service 里做一系列 add/flush/update，最后统一 commit；中途抛异常，get_db 会 rollback。

SQL 注入：为什么不要拼字符串

危险字符串拼接

sql = f"SELECT * FROM assistant WHERE name = '{keyword}'"

如果 keyword 是 ' OR '1'='1，条件永远成立，数据全被查出来。

安全参数化 / ORM

stmt = select(Assistant).where(Assistant.name == keyword)
# 或 text("... WHERE name = :name"), {"name": keyword}

值会被当作数据，不会变成 SQL 语法。

字符集：为什么是 utf8mb4

MySQL 的 utf8 历史上只能存 3 字节，存不了 emoji 和一些生僻字。utf8mb4 才是真正的 UTF-8。项目连接串里显式写了 ?charset=utf8mb4，建表脚本也用它。用户输入 emoji 时不会报错或变问号。

自测：为什么助理列表查询要带 company_id，只按 id 查不行吗？

因为这是多租户系统。如果只按 id 查，A 公司用户猜到 B 公司的助理 ID，就能看到别人的数据（越权 / IDOR）。所有查询都必须带 company_id，这是租户隔离的底线。项目 Repository 的 find_by_id(assistant_id, company_id) 就是这个意思。

ORM = Object Relational Mapping。说人话：把「表的一行」变成「Python 对象」。

Session：一次请求的工作台

Session 是 ORM 的「工作台」：你查出来的对象放在上面，修改会被跟踪，最后统一提交。它不是连接本身，而是连接之上的一层缓存与事务上下文。

方法作用前端类比
db.add(obj)把新对象加入待保存队列把草稿放进购物车
db.flush()把 SQL 发给数据库，但不提交；能拿到自增 ID提交订单预览，还没付款
db.commit()提交事务，真正落库付款成功
db.rollback()撤销本次事务取消订单
db.close()归还连接、清理会话关掉收银台
必懂 flush 不等于 commit。项目里经常先 flush() 拿到审批单 ID，再写范围快照；最后统一 commit()。如果只 flush 不 commit，请求结束会话关闭，数据就没了。

项目里 assistant_repo.py 顶部的 _EAGER 就是干这个的。它用 selectinload 一次性把标签、技能、MCP、知识库、版本记录都加载出来，避免组装卡片时每条都去查一次。

为什么列表要「先查 ID，再批量查对象」？

因为列表要同时满足：多段 UNION 排序、分页、总数、去重。最稳的做法是：

第一步：只查 ID

list_ids 拼出平台 / 自建 / 共享三段，UNION 后排序、分页，得到当前页的 ID 列表和总数。这一步不加载任何关联数据，轻量。

第二步：按 ID 批量加载

load_many(ids) 用 IN (...) 一次查出所有完整对象，并按传入 ID 的顺序重新排序，保证分页顺序不乱。

第三步：批量查授权关系

find_grants 一次查出当前用户对这些助理的授权状态，避免逐条查。

第四步：内存组装

Service 把 ORM 对象 + 授权关系 + 当前用户组装成 AssistantCard，派生按钮、脱敏、折叠状态都在这里完成。

这个模式很常用 「先查 ID + 总数分页，再批量查详情」几乎适用于所有复杂列表。它把「排序分页」和「加载关联」分开，既保证顺序正确，又避免 N+1。

expire_on_commit=False 是什么

SQLAlchemy 默认在 commit 后让对象过期，下次访问属性会重新查库。项目设置 expire_on_commit=False，commit 后对象仍然可用，避免「提交完再组装响应」时又打一堆查询。代价是：同一会话里可能读到缓存，所以 find_by_id 用了 populate_existing=True 强制刷新。

自测：db.add(row) 之后，row.id 什么时候才有值？

执行 flush() 或 commit() 之后。add 只是把对象放进会话，还没发 INSERT；flush 会发 INSERT 并回填自增 ID。项目里 create 方法在 add 后立刻 flush，就是为了让后续逻辑能拿到 ID。

「全部」页签不是简单 SELECT * FROM assistant，而是三类来源合并：

三段各自 select(id, rank, sort_time)，用 union_all 合并，再统一 ORDER BY rank, sort_time DESC, id DESC，最后分页。这样能保证「平台在最前、同状态按时间倒序」的页面规则，而不是在前端排。

    collapsed_status = "approved"

from sqlalchemy import func, select
from sqlalchemy.orm import Session

from app.models.favorite import AssistantFavorite


class FavoriteRepository:
    def __init__(self, db: Session) -> None:
        self.db = db

    def exists(self, company_id: int, user_id: int, assistant_id: int) -> bool:
        return self.db.scalar(
            select(AssistantFavorite.id).where(
                AssistantFavorite.company_id == company_id,
                AssistantFavorite.user_id == user_id,
                AssistantFavorite.assistant_id == assistant_id,
            )
        ) is not None

    def add(self, company_id: int, user_id: int, assistant_id: int) -> None:
        self.db.add(
            AssistantFavorite(
                company_id=company_id, user_id=user_id, assistant_id=assistant_id
            )
        )
        self.db.flush()

    def remove(self, company_id: int, user_id: int, assistant_id: int) -> None:
        row = self.db.scalar(
            select(AssistantFavorite).where(
                AssistantFavorite.company_id == company_id,
                AssistantFavorite.user_id == user_id,
                AssistantFavorite.assistant_id == assistant_id,
            )
        )
        if row is not None:
            self.db.delete(row)
            self.db.flush()

    def count(self, company_id: int, assistant_id: int) -> int:
        return int(
            self.db.scalar(
                select(func.count()).select_from(AssistantFavorite).where(
                    AssistantFavorite.company_id == company_id,
                    AssistantFavorite.assistant_id == assistant_id,
                )
            ) or 0
        )

第 5 步：Service

server/app/services/favorite_service.py（新建）
from sqlalchemy.orm import Session

from app.core.errors import ErrorCode, NotFoundError
from app.core.security import CurrentUser
from app.repositories.assistant_repo import AssistantRepository
from app.repositories.favorite_repo import FavoriteRepository
from app.schemas.favorite import FavoriteResult


class FavoriteService:
    def __init__(self, db: Session) -> None:
        self.db = db
        self.repo = FavoriteRepository(db)
        self.assistants = AssistantRepository(db)

    def _ensure_assistant(self, assistant_id: int, user: CurrentUser) -> None:
        # 必须带 company_id，防止收藏到别的公司的助理
        row = self.assistants.find_by_id(assistant_id, user.company_id)
        if row is None:
            raise NotFoundError(ErrorCode.ASSISTANT_NOT_FOUND, "助理不存在或已删除")

    def status(self, assistant_id: int, user: CurrentUser) -> FavoriteResult:
        self._ensure_assistant(assistant_id, user)
        return FavoriteResult(
            assistant_id=assistant_id,
            favorited=self.repo.exists(user.company_id, user.user_id, assistant_id),
            favorite_count=self.repo.count(user.company_id, assistant_id),
        )

    def add(self, assistant_id: int, user: CurrentUser) -> FavoriteResult:
        self._ensure_assistant(assistant_id, user)
        # 幂等：已收藏就不重复插入
        if not self.repo.exists(user.company_id, user.user_id, assistant_id):
            self.repo.add(user.company_id, user.user_id, assistant_id)
        self.db.commit()
        return self.status(assistant_id, user)

    def remove(self, assistant_id: int, user: CurrentUser) -> FavoriteResult:
        self._ensure_assistant(assistant_id, user)
        self.repo.remove(user.company_id, user.user_id, assistant_id)
        self.db.commit()
        return self.status(assistant_id, user)
并发说明 if not exists 在并发双击时仍可能两个请求同时判断为「不存在」，然后都插入。数据库唯一键会拦住第二个，抛 IntegrityError。生产代码应捕获这个异常并当作「已收藏」返回。这就是「Service 校验 + 数据库约束兜底」的组合拳。

13登录态与权限：前端说了不算

这是后端最重要的安全边界。所有「谁能看、谁能改」的判断都必须在这里。

本项目当前怎么识别用户

开发期没有接真实网关，用请求头模拟：

前端请求拦截器（web/src/api/request.ts）
config.headers.set('X-User-Id', profile.id)          // 1001 / 9001 / 2001 ...
config.headers.set('X-Company-Id', '1')
config.headers.set('X-User-Name', encodeURIComponent(profile.name))
config.headers.set('X-User-Dept', encodeURIComponent(profile.dept))

后端 get_current_user 解析这些头，构造 CurrentUser。正式环境由网关先校验 Cookie / Authorization，再把可信的用户信息注入请求头，服务内部只做解析，不自己做登录密码校验。

重要 这套 Header 方案只适合内网开发期。如果直接暴露公网，任何人都能伪造 X-User-Id: 9001 当管理员。生产必须有网关/签名/JWT 校验，或者至少让内网服务只接受来自网关的流量。

真实登录系统会怎么演进

Session + Cookie

登录后服务端存会话，浏览器带 Cookie。适合同域、传统 Web。

JWT / Token

登录后发一个签名 Token，前端放 Authorization 头。适合前后端分离、多服务。

OAuth / SSO

接入公司统一登录，网关校验后注入用户信息。本项目最终形态接近这种。

不要自己造加密 密码哈希用 bcrypt/argon2，Token 校验用成熟库或网关，不要自己写「加盐 MD5」或「前端加密传密码」。前端加密不能替代 HTTPS，也不能替代后端校验。

中文姓名为什么要百分号编码

HTTP Header 的值按规范只允许 ASCII。前端把「王晓明」用 encodeURIComponent 变成 %E7%8E%8B%E6%99%93%E6%98%8E，后端用 unquote 解码。如果不编码，某些服务器/代理会直接拒绝请求或出现乱码。

自测：管理员能编辑别人创建的助理吗？

按本项目规则不能。管理员的能力是「审批、调整平台助理范围、查看审批」，不是「代替创建人编辑」。update_assistant 明确判断 row.owner_user_id != user.user_id 就抛 403。权限不是「官大什么都能干」，而是按职责细分。

14统一响应与异常：错误也要有格式

前端最怕的不是报错，而是「每个接口报错格式都不一样」。

统一外壳长什么样

server/app/core/response.py
def ok(data: object = None) -> dict:
    """成功响应体；traceId 由中间件在返回前补齐。"""
    return {"code": "OK", "message": "success", "data": data, "traceId": ""}

def fail(code: str, message: str, data: object = None) -> dict:
    return {"code": code, "message": message, "data": data, "traceId": ""}
字段给谁看作用
code前端程序机器可读的结果：OK 或具体错误码
message用户 / 开发人能看懂的提示，可直接 Toast
data前端程序业务数据；错误时可能带 field、missing 等
traceId开发 / 运维把这次请求和后台日志串起来

traceId 是怎么补上的

请求进来→ TraceMiddleware
取 X-Trace-Id 或生成→ 日志上下文 ContextVar→ 响应 render 时填入→ 响应头 X-Trace-Id
server/app/core/json_response.py
class UnifiedJSONResponse(JSONResponse):
    def render(self, content: Any) -> bytes:
        if (
            isinstance(content, dict)
            and "code" in content
            and "traceId" in content
            and not content["traceId"]
        ):
            content["traceId"] = get_trace_id()
        return super().render(content)

所以你写 ok(...) 时 traceId 是空串没关系，真正序列化前会被补上。响应头里也会带同一个 ID，前端可以在报错弹窗里显示「问题编号」，用户截图给开发，开发一搜日志就定位到了。

class ParamInvalidError(BizError):    # 400，可带 field
class ConflictError(BizError):        # 409

Service 里 raise ConflictError(...) 就够了，不需要 import FastAPI 的 HTTPException。这正是分层约束的好处：Service 不依赖 HTTP，换一个入口（CLI/消息队列）仍然能用同一套异常。

HTTP 状态码 vs 业务 code：为什么要两个

HTTP 状态码负责「大类」

  • 浏览器、代理、监控系统都认它
  • 401 能触发前端跳登录
  • 5xx 能触发告警
  • 缓存、重试策略依赖它

业务 code 负责「具体」

  • ASSISTANT_NAME_DUPLICATED 能精确提示
  • 前端可以 switch 处理特殊场景
  • 不改 HTTP 语义也能扩展
  • 日志/埋点可统计

事务边界放在哪里

本项目把事务边界放在 Service：Repository 只 flush，Service 决定什么时候 commit，路由不碰事务。原因很简单：只有 Service 知道「这一组操作是不是一个完整的业务动作」。

并发审批：两个管理员同时点「通过」

假设审批单当前是 pending。管理员 A 和 B 同时打开，同时点通过。如果代码是「先查再改」：

项目用的是条件更新：把「当前还是 pending」作为 UPDATE 的条件，让数据库来裁决。只有第一个请求的 rowcount 是 1，第二个是 0。

幂等：用户双击了怎么办

幂等（idempotent）不是「不报错」，而是「重复执行的结果和执行一次一样」。项目里有两个层面的保证：

层面手段例子
业务层先判断状态，已处理就回放首次结果审批已通过，再点通过返回「已通过」而不是再推进版本
数据库层唯一索引兜底同一助理同一时刻只能有一条 pending 审批；同一用户同一助理只能收藏一次
接口层前端按钮 loading / 禁用减少重复请求，但不能替代后端保证

唯一索引是最后一道防线

Service 里的「先查有没有」只能挡住 99% 的情况，挡不住并发。两个请求可能同时查到「没有」，然后同时插入。这时数据库唯一索引会让第二个失败，事务回滚。

docs/02 · 审批单唯一约束
-- 同一助理同一时刻仅一条 pending，由生成列 + 唯一索引保证
pending_flag GENERATED ALWAYS AS (
  CASE WHEN status = 'pending' THEN 1 ELSE NULL END
) STORED,
UNIQUE KEY uk_approval_pending_assistant (assistant_id, pending_flag)

为什么用生成列？因为 MySQL 唯一索引对 NULL 的处理是「多个 NULL 不冲突」。已处理的审批单 pending_flag 为 NULL，可以有很多条；pending 的为 1，同一助理只能有一条。

不要在事务里做慢操作

不要事务里调外部服务

  • 调大模型（可能 30 秒）
  • 上传 OBS 大文件
  • 发短信 / 邮件
  • 调用不稳定的第三方接口

事务一直不提交，数据库锁和连接被占用，并发一高就雪崩。

推荐先落库，再处理副作用

  • 先 commit 核心数据
  • 再删除旧头像 / 发通知
  • 失败只记日志，不回滚主流程
  • 用补偿任务兜底

项目删除旧头像就是 commit 之后做的，失败不影响助理保存。

死锁：两个事务互相等对方

事务 A 锁了行 1 等行 2，事务 B 锁了行 2 等行 1，谁也动不了。MySQL 会检测到并杀掉一个，抛 deadlock 异常。常见预防：

  • 固定加锁顺序：批量操作时按 ID 升序处理，不要一会儿正序一会儿倒序。
  • 缩短事务：不要在事务里做网络请求、循环几千次。
  • 合理索引：没索引的 UPDATE 会锁很多行，更容易冲突。
  • 失败重试：对 deadlock / lock wait timeout 做有限次重试。

隔离级别，先知道有这回事

级别能避免代价
READ UNCOMMITTED几乎不避免会读到别人未提交的脏数据
READ COMMITTED脏读同一事务内两次读可能不一样
REPEATABLE READ（MySQL 默认）脏读、不可重复读可能出现幻读（InnoDB 用间隙锁缓解）
SERIALIZABLE全部并发性能最差

日常开发不需要背，只要记住：默认级别 + 条件更新 + 唯一索引 + 短事务，已经能解决绝大多数业务并发问题。

自测：审批接口为什么不用「先查状态再更新」？

因为「查」和「更新」之间有时间窗口，两个请求可能都查到 pending。条件更新把判断和写入合成一条原子 SQL，由数据库保证只有一个能成功。第二个请求 rowcount=0，走幂等回放，返回首次结果。

测试会连真数据库吗

会。当前项目的接口测试直接连 .env 配置的数据库，所以跑测试前要先初始化数据库。为了让测试可重复执行，conftest.py 做了两件事：

会话开始前清理

删除名称命中测试前缀的旧助理及其关联数据，避免上次失败的残留影响本次。

会话结束后再清理

删除本次测试新建的助理、审批、范围快照、授权、审计、召唤记录，避免污染开发库。

注意 新增测试时，助理名称要用已登记的前缀（如「接口测试助理%」），或把新前缀加进 _TEST_NAME_PREFIXES。否则测试数据不会被自动清理，日积月累开发库就脏了。

        extra="ignore",                     # 多余键忽略

    cors_origins: str = "http://localhost:5173"

    @property
    def database_url(self) -> str:

        return f"mysql+pymysql://{self.db_user}:{password}@{self.db_host}:{self.db_port}/{self.db_name}?charset=utf8mb4"

    @property
    def cors_origin_list(self) -> list[str]:
        return [item.strip() for item in self.cors_origins.split(",") if item.strip()]
细节为什么
字段名小写 db_hostPydantic Settings 大小写不敏感，对应 DB_HOST
quote_plus(password)密码里可能有 @ # /，不转义会拼坏连接串

改了 .env 没生效？

settings 是模块加载时创建的单例，lru_cache 又缓存了它。改 .env 后必须重启进程（--reload 不一定监听 .env），否则读到的还是旧值。这是很常见的「我明明改了配置」问题。

密钥管理三条底线

① 不进 Git

密码、AK/SK、LLM Key 只放环境变量或密钥管理服务。提交前检查 git diff。

② 不进日志

不要把完整连接串、Token 打日志。日志会被采集、转发、长期保存。

③ 不进前端

前端打包后的代码用户能看。任何 VITE_ 变量都不是秘密，不能放密钥。

联调排错顺序

① 先看请求有没有发出去

Network 里有没有这条请求？没有 → 前端代码/事件/条件渲染问题。

② 再看请求内容

URL、方法、Header、Body 是否和后端契约一致？最常见的是字段名大小写、少传必填项。

③ 看响应状态和 code

200 但 code 不是 OK？说明业务失败。直接看 message 和 data.field。

④ 用 Swagger 对照

同样的参数在 Swagger 能不能成功？能 → 前端问题；不能 → 后端/数据问题。

⑤ 看后端日志 traceId

自测 8 题

1. GET 请求能不能带 Body？

HTTP 协议没有禁止，但语义上 GET 是「查询」，很多代理、缓存、框架会忽略 Body。项目里查询参数一律走 Query，创建/修改走 Body。不要用 GET 传复杂 JSON。

2. 为什么响应要有 code，HTTP 状态码不够吗？

状态码只分大类（400/403/409），业务需要更细的区分。比如同样是 409，可能是重名、状态已变、审批已处理，前端处理方式不同。code 给程序看，message 给人看。

3. Service 里能不能 import FastAPI？

不应该。Service 是业务层，不应该依赖 HTTP。抛项目自己的 BizError，由全局异常处理器翻译成 HTTP 响应。这样 Service 才能被定时任务、CLI、消息消费者复用。

4. flush 和 commit 的区别？

flush 把 SQL 发给数据库但事务未提交，能拿到自增 ID；commit 才真正提交，其他连接才能看到。项目里常先 flush 拿审批单 ID，最后统一 commit。

5. 为什么所有查询都要带 company_id？

多租户隔离。只按业务 ID 查，攻击者猜 ID 就能跨公司访问（IDOR）。这是后端安全的底线，不能依赖前端不传错。

6. 前端已经校验了，后端为什么还要校验？

前端代码用户可改、请求可伪造、接口可被脚本直接调用。前端校验是体验，后端校验才是安全。数据库约束是并发下的最后防线。

7. 为什么审批通过要用条件 UPDATE？

避免两个管理员同时通过导致版本号推进两次、授权重算两次。条件 status='pending' 让数据库原子裁决，只有一个 rowcount=1，另一个走幂等回放。

8. 列表接口为什么不在前端排序？

前端只能排当前页，跨页顺序会乱；分页后也拿不到全量数据。跨页的排序、筛选、统计必须由数据库完成，前端只负责展示。

学习心法 每读一个接口，画一张「请求 → 路由 → Service → Repository → SQL → 响应」的图；每改一个功能，先写一条会失败的测试；每遇到一个报错，先定位层，再改代码。坚持三周，你就能独立接后端需求。
