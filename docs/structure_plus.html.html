先统一说法 全文只用一个词：助理

一句话：本文说的「助理」，就是原型页面上能添加、召唤、共享的那个东西；需求说明书里也写作「助理」，数据库表名与代码标识写成 assistant。 「助理」与 assistant 指同一个东西，本文中文一律叫「助理」，只在提表名 / 字段时保留 assistant。
关于 assistant 这个英文词：它不是另一个东西，只是「助理」的英文标识符。表名、接口路径、错误码、字段名统一用 assistant，与需求说明书、原型代码、数据库脚本保持一致。
读法约定：凡是看到 assistant，一律读作「助理」。例如 assistant.name = 助理名称、assistant_grant = 助理的授权名册、ASSISTANT_NOT_OWNER = 你不是这个助理的创建人。本文所有中文描述一律写「助理」，不再使用「数字员工」这个旧叫法。

关键设计决策 D-01 ~ D-10

编号决策理由代价
D-01共享范围分两层存：申请单（存王晓明勾的组织/角色/岗位/人员）+ 授权名册（存展开后的具体人）申请单满足审批可追溯、不可篡改；名册满足「共享助理」列表查询性能范围变更要重算名册
D-02「移除 / 重新订阅」只改订阅状态，不走审批需求明确重新订阅不触发审批必须把 grant_status 与 subscribe_status 分开
D-03一次勾选 N 个助理共享时，拆成 N 张审批单，共用同一个 batch_no 与同一份范围选择单助理单一待审批申请，状态机最简单批量审批需前端按批次聚合（本期不做）

D-05平台预置助理复用同一套申请单，授权人是管理员且立即生效原型四处范围组件长相一致，后台也统一服务层需按助理来源分支权限校验
D-06助理名称唯一性用「公司 + 名称 + 未删除」唯一索引兜底 + 服务层前置校验并发创建时数据库约束是唯一可靠保证冲突需转业务错误码

③ 两个正交维度：授权是否有效 × 被授权方是否订阅

这两件事由不同的人决定：授权是否有效由审批结果与助理删除决定（系统说了算）；是否订阅由被授权方自己开关（李静说了算）。所以必须分两个字段。

④ 共享范围的两种方式 share_scope.scope_mode

RANGE范围授权

核心机制深解

机制一：一张申请单 → 一份名册（D-01）

share_scope
stage=requested
管理员调整→
share_scope
stage=adjusted
审批通过→
share_scope
stage=effective
按人展开→
assistant_grant
逐人 upsert
为什么分两层
  • 申请单这一层满足审批可追溯：提交时固化，之后组织架构与人员变动不影响已提交的申请，审批详情能原样回放「王晓明当时勾了 O11 + 林晓」
  • 名册这一层满足列表性能：李静打开「共享助理」只需查自己那几行，不必实时递归组织树
范围变化时怎么处理
  • 审批通过时，旧名册集合与新展开集合做差集
  • 新命中人员：插入，或把原有失效行恢复为有效
  • 未命中人员：置失效，不物理删除
  • 曾被移除又被新命中的用户：订阅状态重置为已订阅

机制二：授权 × 订阅双维度解耦（D-02）

谁改哪个维度
  • 授权状态由系统改：审批通过置有效、助理删除或范围收紧置失效
  • 订阅状态由被授权方改：点「移除」/「重新订阅」只动这个字段
为什么拆开
  • 需求明确「重新订阅不触发审批」，授权在审批通过那一刻就已生效
  • 创建人删除助理后授权失效，被授权方即使点「重新订阅」也订不回来 → 返回 GRANT_INVALID，卡片置灰提示

机制三：关键数据一致性规则 C-01 ~ C-11

编号规则实现方式

先澄清一件事：申请单 ≠ 审批单 最容易看错的地方

审批单不是申请单改了个名。点一次「共享」，系统同时生成两条记录：一条记「要共享给谁」（申请单），一条记「批没批、谁批的」（审批单）。 「通过」这个动作只改审批单的状态，申请单上的内容一个字都不动。
📝 申请单 记「内容」 share_scope
  • 回答的问题：要共享给谁
  • 关键字段：scope_mode、stage、四维计数、grant_total
  • 数量：一个助理可以有多张（申请 / 调整 / 生效各一张）
  • 谁会改它：没人改。要变就新开一张
  • 原型在哪看：共享弹窗里勾的人、「授权范围预览」chips
  • 它没有：通过 / 拒绝 / 审批人 / 拒绝原因 —— 这些都不在申请单里
✅ 审批单 记「决定」 approval
  • 回答的问题：批没批、谁批的、为什么拒
  • 关键字段：status、submitter、approver、reject_reason、requested_scope_id、final_scope_id
  • 数量：同一助理同一时间只有一张待审批
  • 谁会改它：审批人点通过 / 拒绝时改 status
  • 原型在哪看：审批中心里的那一行（列表视图）或那一张卡（卡片视图）
  • 它没有：组织 / 角色 / 人员明细 —— 只存一个指针指回申请单
怎么验证它们是两条记录？看字段就知道：审批单里没有「给谁」的字段，只有一个 requested_scope_id = 5001 的指针，指向那张申请单；申请单里也没有「通过 / 拒绝」的字段。两边字段完全不重叠，只靠一个指针相连 —— 说明它们从设计上就是两条独立的记录。

为什么不能少一张表？删掉哪张会出什么事

删掉 share_scope

审批详情就无法回放「申请时提交了什么范围」。若审批过程中组织架构调整过，就无法追溯原申请，也无法记录管理员审批前的「调整草稿」。

删掉 share_scope_item

只知道「总共 2 人」，不知道「是哪个组织的哪个人」，审批详情里的四维明细和范围摘要都渲染不出来，也没法在审批时按维度调整。

删掉 approval

没有「状态机」载体，无法区分待审批/已通过/已拒绝/已终止，无法做幂等决策，也无法支撑审批中心的列表与角标。

删掉 assistant_grant

被授权方每次打开「共享助理」都要实时递归组织树算「我是否在范围内」，性能不可接受；也无法记录「我移除了」这个人员级状态。

常见困惑 FAQ

Qshare_scope 和 share_scope_item 有什么区别？为什么不能合成一张表？
share_scope 是一张申请单的整体（方式 RANGE/PUBLIC、stage、四维计数、展开人数），share_scope_item 是单子上的每一行（dim=org 且 item_id=O11 这样）。
合成一张的坏处：四维是 1:N 关系，合成后要么把四维塞进 JSON（失去按维度查询/统计能力），要么一行里塞多值（违反 1NF，无法建唯一索引）。
拆开的好处：share_scope 上的计数是冗余的，能让「审批中心列表展示范围摘要」只 join 主表、不看明细，性能更好。
Q同一助理为什么会有多张 share_scope？
因为 stage 三态：requested（提交时）、adjusted（审批前管理员调整）、effective（最终生效）。每次调整都新开一张，旧的保留。一个助理在生命周期里可能有很多张，分别对应不同次共享 / 变更。
所以查授权时不能只按 assistant_id 定位，必须同时限定 stage='effective'（或通过 approval.final_scope_id 反查）。
Qapproval 的 requested_scope_id 和 final_scope_id 都是必填吗？
都不是必填，但语义不同：
· requested_scope_id：审批单创建时就有值（指向申请态那张单）
· final_scope_id：审批通过时才回填（指向生效态那张单）
若助理是「管理员直接配置」共享的（无审批单，如平台预置助理的「授权范围」），则 final_scope_id 为空，此时用 share_scope 表里 approval_id IS NULL AND stage='effective' 来识别。
Qassistant_grant 里既没有组织也没有角色，那怎么知道一个人是被谁授权的？
靠 source_scope_id 反向追溯：assistant_grant.source_scope_id → share_scope.id → share_scope_item，就能知道这个人是通过「组织 O11 递归展开」还是「人员 u5 直接选中」进来的。
为什么不在名册里冗余存来源？因为一个人可能同时被多个维度命中（林晓既在 O11 下，又被直接勾选），来源是多值的，冗余存就要重复行。设计上用 source_scope_id 指回申请单，需要追溯时再 join 明细即可。
Q被授权方移除订阅后，为什么名册里那行还在？
因为名册上有两个正交维度：授权是否有效、是否订阅。移除订阅只是被授权方的个人行为，授权并没有被撤销，所以只改订阅状态为「已移除」，行保留。
好处：① 可以随时「重新订阅」，不需要重新走审批；② 创建人查看「授权给了哪些人」时仍能看到完整名单；③ 审计能追溯。
Q一个助理最多会有几条 approval 记录？
无限条（生命周期内每次共享 / 范围变更各一条），但同一时刻最多一条待审批（uk_approval_pending_assistant 兜底）。这条唯一索引是整个授权流程并发安全的基石，防的是「两个管理员同时点通过」或「用户连着点两次共享」。
Q管理员直接调整范围，为什么没有 approval 记录？
需求上管理员有权直接配置平台预置助理与本公司的共享范围，属于即时操作，不产生审批。所以这类操作只写 share_scope(stage='effective', approval_id=null) + 重算名册 + 写版本记录。
这就是「approval_id 为空且 stage='effective' 表示管理员直配」这条特殊约定的由来。
Q公开模式（PUBLIC）下，名册是怎么处理的？
按当前设计（待确认 Q-05）：不逐人落库，只在 share_scope.grant_total 里记录公司在职人数。被授权方查询「共享助理」时，服务层对 share_status=approved 且生效单为 PUBLIC 的助理整体可见。
某个人移除订阅时，再落一条「已移除」的例外记录。好处：避免全公司上万人逐人落行；代价：查询 SQL 与移除逻辑要特判 PUBLIC 分支。

用一句话把四表串起来

参数类型默认说明
scopeenumallall 全部 / mine 我的助理 / shared 共享助理
categoryIdint—分类筛选，对应页面分类页签，不传为「全部」
keywordstring—按助理名称与标签模糊搜索，≤50 字符
statusFilterenum—仅 scope=mine 生效：unshared / pending / approved / rejected
subscribeFilterenumsubscribed仅 scope=shared 生效：subscribed / removed
page / pageSizeint1 / 12pageSize 最大 50

卡片响应字段：assistantId / name / avatar* / categoryName / tags / description / source / shareStatus / subscribeStatus / version / ownerName / authorizedCount / createdAt / updatedAt / actions。不含 prompt。

actions 派生规则（决定卡片上出现哪些按钮）

场景actions
自建 + 未共享summon, edit, delete, share
自建 + 待审批summon, edit, delete
自建 + 已共享summon, edit, delete, shareScope（页面文案「共享范围」）
自建 + 已拒绝summon, edit, delete, resubmit（页面文案「重新提交」）
平台预置 + 管理员 / 非管理员summon, shareScope / summon
共享 + 已订阅summon, remove
共享 + 已移除 且授权有效 / 失效resubscribe / []（卡片置灰并提示「该助理授权已失效」）

排序：all = 平台预置 → 我的助理 → 共享助理（各段内部倒序）；mine 按创建时间倒序；shared 按授权时间倒序。

POST /shares 提交共享申请

统一入口，覆盖首次共享、被拒后重新提交、批量勾选提交。对应原型「共享提交」与「重新提交共享审批」两个弹窗。

{
  "assistantIds": [1001],
  "scope": {
    "scopeMode": "RANGE",
    "orgs": ["O11"], "roles": [], "positions": [], "users": ["u5"]
  },
  "changeNote": "首次申请共享，覆盖招聘组与薪酬绩效组"
}

校验顺序

步校验错误码
1assistantIds 非空、去重、≤20PARAM_INVALID
2每个助理存在、未删除、属于当前公司、创建人为当前用户ASSISTANT_NOT_FOUND / ASSISTANT_NOT_OWNER
3每个助理状态 ∈ {未共享, 已拒绝}ASSISTANT_ALREADY_SHARED
4该助理无待审批单ASSISTANT_STATUS_CHANGED
5范围授权时至少 1 项；四维上限SHARE_SCOPE_EMPTY / SHARE_SCOPE_EXCEED_LIMIT
6展开人员成功（主数据可用）INTERNAL_ERROR

副作用（单事务）：① 每个助理各建一条待审批单，共用 batch_no；② 每个助理写一张申请态的单子 + 明细；③ 批量更新 assistant.share_status=pending；④ 写版本记录 share_submit；⑤ 写审计；⑥ 失效审批中心角标缓存。

PUT /assistants/{assistantId}/share-scope 调整共享范围
场景条件行为响应
A. 创建人调整已共享助理自建 且 已共享 且为创建人新建一条范围变更审批单（待审批）；助理状态 保持已共享不变202 applied:false
B. 管理员调整isAdmin=true直接写一张生效态的单子（approval_id 为空），重算名册（差集失效），次版本 +1200 applied:true
C. 平台预置助理source=platform仅管理员可操作，同 B200
D. 被授权方非创建人且非管理员拒绝403

GET 回显接口返回 editableBy：direct（管理员即时生效）/ approval（创建人走审批）/ none（不可编辑）。存在进行中的范围变更审批时 pendingApprovalId 有值。

POST /approvals/{approvalId}/approve 审批通过

Header Idempotency-Key（推荐）。对应审批详情页底部「审批通过」。

条件更新状态
UPDATE approval SET status='approved', approver_*, final_scope_id=? WHERE id=? AND status='pending'；影响行数为 0 时读当前状态，已是已通过则返回首次结果（幂等），否则 APPROVAL_ALREADY_HANDLED
确定最终范围
优先取调整态，否则取申请态；为空时降级为申请态
按人展开为名册
新增人员插入；已有人员恢复有效；新集合未命中的原有效人员置失效（不物理删除）；本次新命中且曾被移除的用户订阅状态重置为已订阅
回写助理
更新 share_status='approved'、authorized_count、次版本 +1
写流水
共享申请写 share_approve；范围变更写 scope_change；写审计（含变更前后范围），失效角标缓存
POST /ai/generate AI 生成 / 润色

对应原型四个「✨AI 生成」按钮：描述、自定义标签、提示词、召唤快速问题。

field为空（生成）已有内容（润色）输出约束
description依据助理名称 + 分类生成在现有描述基础上润色补充10-200 字符
tags依据名称 + 描述生成 5 个基于已有标签补充至 5 个每个 ≤8 字符，总数 ≤5，去重
prompt依据名称 / 描述 / 分类 / 标签生成结合名称、描述润色补充≤4000 字符
quickQuestions依据名称 + 描述生成在已有基础上润色补充去重合并，≤6 条
  • 标签已满 5 个 / 快速问题已满 6 条 → 200 + hitLimit: true，value 为原值
  • 大模型超时 / 失败 → 502 AI_GENERATE_FAILED，前端保留原内容
  • 服务端超时 8s；不参与助理保存事务；不落库

前后端交互约束

防抖与幂等
  • 提交类按钮请求期间 loading 且禁用
  • 审批与订阅接口额外带 Idempotency-Key
列表三态
  • 加载中 / 空态 / 加载失败（可重试），由 code 区分失败类型
失败与状态漂移
  • 创建 / 编辑 / 共享提交失败时不清空向导内容与已选范围
  • 409 类错误（状态已变更 / 已被处理 / 已删除）统一提示并刷新当前列表
一致性与刷新
  • 四处共享范围场景共用同一组件，提交体均为统一的 scope 结构
  • 提交共享 / 审批决策 / 移除订阅成功后，就地刷新受影响列表与角标，不整页重载
  • 401 → 跳登录 → 回跳并保留 scope/categoryId/keyword（存 sessionStorage）
